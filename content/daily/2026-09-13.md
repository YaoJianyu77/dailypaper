## Latest paper 1 — HipKittens: Fast and Furious AMD Kernels

**MLSys · 2026-05-18 · William Hu, Drew Wadsworth, Sean Siddens, Stanley Winata, Daniel Y. Fu, Ryan Swann, Muhammad Osama, Christopher Ré, Simran Arora.** [Official publication](https://proceedings.mlsys.org/paper_files/paper/2026/hash/bc75fa9843a7905bbed9d83895a88f7f-Abstract-Conference.html) · [Full paper (1/3)](https://proceedings.mlsys.org/paper_files/paper/2026/file/bc75fa9843a7905bbed9d83895a88f7f-Paper-Conference.pdf) · [Full paper (2/3)](https://proceedings.mlsys.org/paper_files/paper/2026/file/bc75fa9843a7905bbed9d83895a88f7f-Supplemental-Conference.pdf) · [Full paper (3/3)](https://arxiv.org/pdf/2511.08083)

### 1. Paper in brief

[HipKittens: Fast and Furious AMD Kernels](https://proceedings.mlsys.org/paper_files/paper/2026/file/bc75fa9843a7905bbed9d83895a88f7f-Paper-Conference.pdf) presents a C++ library for efficient AMD GPU kernels. Existing compilers can mishandle registers and memory instructions, while NVIDIA scheduling templates fit AMD's resource allocation poorly. The authors retain tile programming but redesign its implementation around AMD: explicitly controlled registers, instruction-specific memory layouts, alternating computation and loading, and scheduling that respects chiplet caches. On MI355X, noncausal grouped-query attention (GQA) backward reaches 2.49× the strongest plotted baseline at sequence length 8192. The contribution is a reusable set of programming mechanisms backed by hardware analysis and kernel experiments. Performance remains workload-dependent, and achieving it still requires explicit scheduling choices; the library does not automatically remove architecture-specific tuning. (§§3–4.)

### 2. Problem and core insight

HipKittens computes matrix products and Transformer attention outputs or gradients, targeting high throughput with correct operator results on AMD CDNA GPUs. A wave contains 64 threads; four SIMD execution units share each compute unit's resources.

Two observations drive the design. First, AMD statically divides registers among resident waves. Dedicated loading waves therefore consume registers while contributing no output, restricting the output tile and arithmetic intensity. Compilers also restrict usable register instructions. The consequence is to expose tile placement and let every wave perform computation while overlapping memory movement. (§§3.2–3.3, pp. 4–7.)

Second, each compute chiplet has a local L2 cache, while chiplets share a last-level cache (LLC). Improving local reuse can disrupt reuse across chiplets. Work assignment must coordinate both levels rather than maximize one hit rate. (§3.4, pp. 7–9.)

### 3. How the method works

For matrix multiplication, inputs travel from high-bandwidth memory (HBM), through shared memory and register tiles, into matrix fused multiply-add (MFMA) instructions; accumulated output tiles return to HBM. Tile types specify dimensions, datatype, layout, and underlying MFMA shape, so bulk operations expand into suitable hardware instructions. (§3.2, pp. 4–6.)

Register pinning optionally assigns tiles explicit physical register ranges. Generated inline assembly can feed accumulator registers directly into MFMA operands, avoiding compiler-generated transfers into vector registers. Shared-memory address permutations, called swizzles, distribute simultaneous accesses across banks. Because AMD instructions use different participating thread groups and layouts, HipKittens supports compatible groups of access patterns instead of one universal permutation. Direct asynchronous HBM-to-shared loads bypass registers. (§3.2; supplement §§D.1–D.4, pp. 23–25.)

An eight-wave block places two waves on each SIMD. A conditional barrier initially delays one group of four; subsequently the groups alternate computation and memory stages. Both groups contribute output, preserving registers for useful tiles while hiding load latency. Wait instructions check outstanding-load counters before data are consumed, and barriers maintain stage order (supplement §D.6, p. 26). For imbalanced workloads, a four-wave alternative interleaves smaller memory and compute operations within each wave, requiring more detailed code. (§3.3, pp. 6–7.)

Before computation, block indices are remapped assuming round-robin assignment across chiplets. A chunk parameter groups related work onto the same chiplet; a window parameter arranges output tiles to reuse matrix inputs. Joint tuning also aligns accesses across chiplets for LLC reuse. (§3.4, Algorithm 1.)

Attention applies the same scheduling to query, key, and value tiles. It computes scaled query–key products, updates online-softmax maxima and normalization sums, rescales the running output, and accumulates weighted values. Vector softmax operations interleave with matrix operations. Backward kernels combine different MFMA shapes, shared-memory layouts, and pinned registers. (§4, p. 10; supplement §E.3, pp. 33–36.)

### 6. Contributions and limitations

The contribution combines hardware characterization, reusable scheduling patterns, and an implemented tile library. Multi-head attention (MHA) backward and some GEMM shapes still lose to vendor baselines (Table 1, p. 5; Figures 7 and 16, pp. 9, 19). Portability requires adaptation: MI325X uses register buffering because shared memory cannot support the illustrated double buffer (supplement §E.1, p. 27). Register pinning removes compiler safety guarantees, and preliminary FP6 kernels require manual dependency spacing (§D.4 and §F, pp. 25, 37–38).

Version evidence matters: the official paper names the Pile for its separate training-stability test, while arXiv v1 names SlimPajama; their FP6 plots also differ (pp. 10, 38, 51, 79). Reported results here follow the proceedings and supplement.

### 7. Final assessment

Interpretation. HipKittens convincingly demonstrates that reusable tile abstractions can deliver competitive AMD kernels when register allocation, instruction scheduling, and cache placement reflect the hardware. Its strongest evidence combines cache ablations with substantial GQA gains. General deployment benefits are less certain because training measurements omit essential configuration details and kernel tuning remains manual. The principal contribution is systems design and engineering, with conclusions strongest for the evaluated CDNA workloads.

## Latest paper 2 — Presto: A Match-Action TCP Stack for the Terabit Era

**SIGCOMM · 2026-08-11 · Rajath Shashidhara, Antoine Kaufmann, Simon Peter.** [Official publication](https://api.crossref.org/works/10.1145%2F3789240.3829111) · [Full paper](https://arxiv.org/pdf/2504.19058)

### 1. Paper in brief

Presto moves established TCP connections into programmable match-action hardware while exposing ordinary POSIX sockets. Software stacks spend substantial CPU time processing dependent connection state; conventional hardware offloads sacrifice programmability. Presto reorganizes those dependencies through speculative updates validated downstream and payload-free synthetic segments that complete backward updates. Payloads reside in host memory, allowing the hardware pipeline to process packets without transport buffering. On a Tofino 2 testbed, a 64-byte echo benchmark reaches nearly 40 million operations/s, 1.67× the TAS kernel-bypass TCP stack, with 18 μs median and 24 μs 99.99th-percentile latency (§5.1.1, p. 8). The contribution is a programmable TCP architecture with efficient application integration. Its production implications remain qualified by omitted payload checksums, prototype recirculation, and simulation-only selective-recovery evaluation.

### 2. Problem and core insight

The objective is reliable, ordered byte-stream delivery at high packet rates with little host processing. Presto targets persistent datacenter connections, short remote procedure calls (RPCs), and congestion-driven loss. Reconfigurable Match-Action Table (RMT) hardware executes fixed stages with local state and forward-only information flow. Updating a receive sequence number requires window information stored downstream; delaying the update creates a backward dependency, while locking serializes packets (Figure 1).

Two insights resolve this mismatch: compliant senders make optimistic window updates practical if validation precedes delivery; and backward updates can be encoded as new forward-moving events that reuse normal TCP processing. Together they preserve pipeline concurrency within individual connections (§§2–3).

### 3. How the method works

Network segments, host payloads, and synchronization events → classification and connection lookup → scheduling/header preparation → receive/transmit-window processing → host-memory placement or network transmission. These RX, TX, and SYNC workflows share one pipeline. Only the lossless egress portion mutates protocol state, so earlier traffic-manager drops behave like recoverable network loss. A CPU control plane manages connection lifecycles and congestion policy (§3, pp. 3–4).

On reception, Presto removes duplicates and speculatively advances the next expected sequence number before validating available window space. A violating segment is discarded; the receiver advertises a zero window while the control plane restores state. Validated out-of-order payloads go directly into host buffers through direct memory access (DMA), but application notifications expose contiguous data only (§3.1).

The default OOO-1 design tracks one out-of-order interval using two boundaries relative to the next expected byte. Closing its gap requires updates to earlier stages. A mirrored, payload-free pseudo-segment represents the newly contiguous interval and completes those updates through ordinary receive logic. Duplicate trimming prevents double accounting if another segment advances state first. Merge events can piggyback on acknowledgment events. Additional intervals consume more stages; disjoint arrivals exceeding tracking capacity are dropped (pp. 4–6).

For transmission, the control plane computes Data Center TCP (DCTCP) rates from acknowledgment and congestion-mark statistics. Hardware-generated SYNC messages grant credits; libPresto pushes eligible buffered data immediately, avoiding a separate fetch round trip. Three duplicate acknowledgments trigger fast retransmission and reduced credits; SYNC also signals timeouts. Consumption releases receive-window space through SYNC. Ordinary sockets copy application buffers, whereas libPresto-ZC exposes buffers directly. The switch prototype uses unreliable RDMA writes solely for DMA; Presto supplies transport reliability, ordering, and congestion control (pp. 6–7).

### 5. Experimental evidence

The testbed uses eight 32-core Xeon Gold 6430 hosts at 2 GHz, 256 GB RAM each, ConnectX-6 adapters configured at 100 Gb/s, and a Tofino 2 switch. Baselines are Linux TCP, kernel-bypass TAS, and RDMA. Hardware tests default to OOO-1 reception, go-back-N recovery (retransmitting unacknowledged suffixes), and DCTCP. Exact tested software versions: Not specified in the paper. (§5, pp. 7–8.)

1. **RPC processing:** The 32-core echo test uses one outstanding 64-byte RPC per connection and produces the brief's throughput/latency results. Separate 8-byte RPC scaling approaches 1 billion pipeline packets/s with two added TAS clients; each Presto-to-Presto RPC generates eight processing events. This measures aggregate pipeline work, not one billion completed RPCs (§5.1, pp. 8–9).

2. **Streaming and storage:** With 1 MB bursts from TAS-nocopy and one receiving core discarding payloads, Presto-ZC matches RDMA's approximately 25 million packets/s ceiling for small segments, versus approximately 5 million for TAS's low-level interface, which still copies payloads. Larger segments hit the 100 Gb/s link ceiling. The stated 1.6 Tb/s is an extrapolation at 8 KB MTU. SPDK's single-core, RAM-backed 4 KB random-write test also approaches RDMA until CPU saturation; MTUs are 4,096 bytes for Presto/RDMA and 4,400 for Linux. Presto retains credit-grant and client-copy overheads (§5.2, pp. 9–10).

3. **Application efficiency:** FlexKVS uses one million uniformly accessed key-value pairs, 8-byte keys, 64-byte values, and a reported 0.99 GET:SET ratio. Across five-minute runs varying threads/connections, Presto's best reported throughput-per-watt doubles TAS's; its worst exceeds TAS's best by 1.2× at 5× lower 99.99th-percentile latency. Switch-power differences stay within 4 W, supporting reduced host work as the primary gain (§5.1.3, p. 9).

### 6. Contributions and limitations

The contribution combines protocol decomposition, bounded reassembly, and application integration. Programmable extensions include delayed acknowledgments, Timely congestion measurements, and shared-log placement; an FPGA egress-pipeline port supports architectural portability, although compared FPGA stacks implement different TCP subsets (§§5.3–5.5).

The prototype omits TCP payload checksums and RDMA integrity checks and requires sender Ethernet padding. Host–switch DMA relies on Priority Flow Control; same-switch Presto endpoints require recirculation, and connections cannot cross pipelines (§4.1). These restrictions qualify compatibility claims. Selective acknowledgments/recovery are evaluated in ns-3 because compiler problems prevent hardware evaluation (pp. 8, 12). Finite reassembly state limits tolerance of reordering; zero-copy transmission can block behind earlier allocations. Multipath operation remains unevaluated (§7).

### 7. Final assessment

Interpretation. Presto convincingly shows that dependent TCP processing can exploit programmable pipeline parallelism while retaining familiar application interfaces. Its strongest evidence combines packet-rate measurements with application efficiency. Its weakest point is the distance between the constrained prototype and a complete production transport. The architectural result is persuasive for persistent datacenter traffic; deployed interoperability, comprehensive loss recovery, and end-to-end terabit throughput remain incompletely established.

## Latest paper 3 — KUNSERVE: Parameter-centric Memory Management for Efficient Memory Overloading Handling in LLM Serving

**EuroSys · 2026-04-26 · Rongxin Cheng, Yuxin Lai, Xingda Wei, Rong Chen, Haibo Chen.** [Official publication](https://api.crossref.org/works/10.1145%2F3767295.3769348) · [Full paper (1/2)](https://ipads.sjtu.edu.cn/_media/publications/kunserve-eurosys26.pdf) · [Full paper (2/2)](https://arxiv.org/pdf/2412.18169)

### 1. Paper in brief

KUNSERVE handles bursts that exhaust GPU memory during large language model inference. Existing systems evict, swap, or migrate the key/value cache (KVCache) holding request state, but cluster-wide shortages still force requests to wait. KUNSERVE instead temporarily removes redundant model weights across replicas, converts their memory into cache capacity, and executes the unchanged model cooperatively through pipeline parallelism. A planner limits cooperation, while transfer prioritization and balanced microbatches control its overhead; weights return when pressure subsides. The authors report up to 72.2× lower P99 time to first token (TTFT) in their evaluated overload scenarios, with some increases in time per output token (TPOT). The contribution is an adaptive memory-management system that exchanges replication for burst capacity, with finite headroom and transition costs (§§3–5).

### 2. Problem and core insight

The input is a stream of prompts; the output is generated tokens subject to latency service-level objectives (SLOs). A serving instance is the smallest GPU set holding one complete model. Replicated instances normally serve independently. Unfinished requests retain growing caches, so transient demand can exceed high-bandwidth memory (HBM) even when average utilization is modest (§2, pp. 3–4).

Two observations drive the design. Weights occupy substantial HBM, making them a useful reserve. Those weights are duplicated across instances, allowing a group to retain complete layer coverage while discarding redundant copies. Requests then traverse the surviving layers; model computations remain intact, but communication replaces independent execution (§3, p. 5).

### 3. How the method works

Prompts enter the dispatcher, join instance queues, pass through prefill and iterative decoding, and produce streamed tokens. The monitor tracks memory pressure and invokes the global manager when overload occurs (§3, Figure 4).

The drop planner repeatedly merges the two smallest instance groups and removes duplicated layers until it satisfies queued-request memory demand. Every merged group retains a complete model. The greedy search favors short pipelines and costs O(N log N) for N instances. If insufficient redundant weights remain, cache-based handling and autoscaling provide fallback (§4.1, p. 6).

Local managers repurpose freed physical memory through CUDA virtual-address mappings, extending the cache’s contiguous address range so existing attention kernels remain usable. For example, two replicas can retain complementary layer halves and jointly execute each request. Pipeline parallelism transfers intermediate activations between these halves; tensor parallelism within an instance remains possible (§§3–4.1).

Ongoing requests must exchange layer-specific caches with their new execution destinations. These requests pause while newly admitted requests use the GPUs. The network coordinator chunks cache transfers, yielding between chunks to latency-critical activations. On the evaluated 200-Gbps network, affected requests typically pause 1–2 seconds. Interpretation: average TPOT can hide that streaming interruption (§4.2, p. 7).

To reduce idle pipeline intervals, or bubbles, the scheduler looks across queued requests and recursively splits them into microbatches with similar predicted execution times. For c new tokens following p prefix tokens, its estimate includes α[pc+c(c+1)/2]+βc+γ: prefix attention, causal self-attention, feed-forward computation, and fixed overhead. Coefficients come from offline least-squares profiling. Equal token counts would miss the attention costs; a minimum batch size prevents excessive splitting (§4.3, pp. 7–8).

When usage falls below the configured 50% threshold relative to the undropped configuration, missing weights return from peers while serving continues. Activation transfers again receive priority. This restores independent execution and removes unnecessary pipeline overhead (§4.4, p. 9).

### 5. Experimental evidence

Cluster A has eight servers, each with one 80-GB A800 and 200-Gbps RDMA. Cluster B has two servers with eight 80-GB H800s each, 300-GB/s NVLink and 400-Gbps RDMA; bandwidths are unidirectional. Qwen-2.5-14B uses single-GPU instances; 72B uses four-GPU tensor-parallel instances. Both use grouped-query attention. BurstGPT arrivals are rescaled while preserving temporal patterns and keeping average memory demand below 60%. Mean input/output lengths are 642/262 for BurstGPT, 1,660/373 for ShareGPT, and 5.9K/499 for LongBench (§5.1, Tables 1–2).

Baselines are vLLM 0.6.3 with independent replicas or fixed two-stage pipelines, Llumnix 0.1.0, and InferCept upgraded with the authors’ scheduler and attention backend; vLLM uses block size 64. CUDA/PyTorch versions and repeat counts: Not specified in the paper.

**Latency trade-off.** The authors report up to 72.2× lower P99 TTFT against cache-based baselines; separately, LongBench-72B yields 8.4–11.9× reductions. Gains come from admitting requests previously queued for memory. LongBench-14B P50 TPOT rises 15.8–22.7% against the non-pipelined baselines; Figure 13’s static-pipeline exception prevents interpreting the headline as universal (§5.2, pp. 11–12).

**Mechanism ablation.** On LongBench-14B bursts, dynamic dropping reduces P99 TTFT 11.7× versus independent vLLM replicas; coordinated exchange adds a 1.5× reduction. Lookahead then lowers bubble time from 21.9% to 8.3% and raises throughput 20%, supporting the scheduling explanation (§5.3, p. 12).

**Restoration.** Across a 640-second BurstGPT run, restoring weights lowers median TTFT/TPOT 28%/23% and P99 TTFT 6.4× versus KUNSERVE without restoration. Retaining pipelines would reduce throughput between bursts and worsen subsequent pressure (§5.5, p. 13).

### 6. Contributions and limitations

The conceptual contribution is treating replicated weights as reclaimable capacity; virtual-memory remapping, coordinated transfers, and cost-based scheduling make it executable. Capacity remains bounded: sustained overload eventually needs more instances. Lookahead depends on an existing queue, so waiting to form batches under light load can increase latency. Evaluation covers two dense models; mixture-of-experts compatibility is argued, not measured (§§5.6–6).

Grouping also enlarges the failure domain. The design restores affected replicas from host-memory or SSD weight copies, but provides no failure experiment. Recovery latency and in-flight request recovery details: Not specified in the paper. Interpretation: weaker networks and strict limits on individual token gaps could substantially reduce its appeal (§4.4).

### 7. Final assessment

Interpretation: KUNSERVE convincingly demonstrates that temporarily reclaiming redundant weights can suppress memory-induced queueing in replicated GPU serving. Its strongest evidence combines workload-level latency measurements with ablations of the supporting mechanisms. The main uncertainty is how transition stalls and larger failure domains behave under stricter streaming requirements or broader deployments. This is a systems contribution best supported for transient bursts, dense models, and fast inter-instance networks.

## Latest paper 4 — OptCCL: Scalable Synthesis of Optimal Collective Communication Algorithms

**SIGCOMM · 2026-08-11 · Richard Shapley, Rachit Agarwal, David Shmoys.** [Official publication](https://api.crossref.org/works/10.1145%2F3789240.3829207) · [Full paper](https://www.cs.cornell.edu/~ragarwal/pubs/optccl.pdf)

### 1. Paper in brief

OptCCL synthesizes collective communication schedules for specified GPU, host, and network resources. Earlier synthesizers couple routing with every transmission step, making fine-grained pipelining expensive to optimize. OptCCL instead optimizes routes under aggregate bandwidth constraints, then constructs a chunk schedule; symmetry reduces the routing search further. Its guarantees concern a bandwidth-dominated model, with bounded overhead for finite chunks. In simulated AllGather experiments, algorithmic bandwidth reaches 18× TACCL’s in the strongest comparison, while the main NVLink configurations scale to 256 GPUs (Figure 4, p. 11). The contribution is an optimization framework supporting heterogeneous capabilities and concurrent collectives. Real GPU execution and end-to-end ML gains remain unvalidated (§9, p. 12), and supplementary experiments qualify the synthesis scalability claim (technical report §A.13).

### 2. Problem and core insight

Inputs specify topology, component capabilities, collective demands, message size, and chunk size; outputs specify chunk routes and transmission orders. The primary objective is completion time, or makespan when collectives share resources. A secondary objective minimizes weighted traffic, by default transfers into and out of GPUs (pp. 2–3).

Two observations drive the design. First, sufficiently fine pipelining lets aggregate link budgets determine achievable completion time without optimizing every transmission instant. Second, sources equivalent under the topology, capabilities, costs, and collective definition admit equivalent optimization subproblems. These observations remove temporal detail and redundant source problems while preserving the routing optimum (§4.1; §6).

### 3. How the method works

Topology and demands → directed graph → routing optimization and feasibility checks → tree decomposition → chunk scheduling. Vertices separately support storing, transmitting, copying, and reducing data. Constraints can cover groups of edges, representing shared memory bandwidth (pp. 2–3).

The linear program, or LP, gives each source–destination pair a flow. For AllGather, which distributes every source’s data to all destinations, usage variables account for shared copies: several destination flows can represent one physical transmission. LP(9) constrains total usage on link group L to R·b(L), where R is target completion time and b(L) its bandwidth. Auxiliary flow problems determine R. Layers bound route length rather than fine-grained time slots (§4.1, p. 5).

Fractional flows can incorrectly merge different data fragments. OptCCL decomposes routes into trees and checks their actual traffic against usage variables. Violations trigger vertex duplication and re-solving. With copying permitted at every component, the initial relaxation suffices for ideal topologies: optimal routes traverse at most four links, with bandwidth limits and costs confined to inter-host links (§4.2, p. 6).

Mirrored Dantzig–Wolfe decomposition coordinates smaller source problems through shared bandwidth constraints. It solves one representative per symmetry class and maps its solution to equivalent sources (§6). Weighted fair queueing then prioritizes chunks by their virtual finish times, emulating the fractional routing rates. Fixed chunks introduce bounded overhead; the authors report completion within 1% of the optimum in evaluated scenarios (§4.3, p. 7).

AllReduce combines inputs and distributes the result. OptCCL jointly chooses where ReduceScatter places reduced fragments and overlaps their dissemination: each completed reduction chunk immediately enters AllGather. Independent concurrent collectives share one bandwidth budget and makespan objective. Components lacking copy or reduction capability receive corresponding restrictions (§5, pp. 7–9).

### 5. Experimental evidence

Communication is simulated on A100 and DOE topologies with eight and four GPUs per host, respectively, using multi-rail networking; Figures 4–5 include NVLinks. Synthesis runs on a server reported as a 32-core Intel Xeon Gold 6234 with 314 GB RAM. Baselines use their largest chunk count completing synthesis within three hours. OptCCL timing generates representative schedules per symmetry class. Exact experimental message/chunk sizes, link bandwidths, and solver version: Not specified in the paper. (§7, p. 10.)

First, AllGather algorithmic bandwidth—message size divided by completion time—is 1–5× TE-CCL’s, 1–1.6× SyCCL’s, and 1.2–18× TACCL’s across evaluated configurations. These are ranges, not averages (Figure 4, p. 11).

Second, at 64 or more GPUs, AllGather synthesis is 3–32× faster than SyCCL and 5–60× faster than TACCL. The separately retrieved [technical report](https://github.com/ml-collectives/optccl/blob/main/optccl-techreport.pdf), Table 3, p. 22, isolates symmetry’s contribution: at 32 GPUs, standard versus mirrored decomposition takes 34,700 versus 82.2 seconds; its topology: Not specified in the paper.

Third, Table 2 tests 64 GPUs across two pods: eight All-to-All, sixteen ReduceScatter, and thirty-two point-to-point communications, with the latter workload sizes reported as twice All-to-All’s. All approaches use OptCCL. Sequential/overlaid/joint completion times, normalized to joint optimization, are 6.25/1/1 with NVLinks and 4.87/1.31/1 without. Concurrency supplies most of the benefit; joint routing adds value without NVLinks (§7.2, p. 11).

### 6. Contributions and limitations

The contribution combines an aggregate-flow formulation, feasibility refinement, and symmetry-preserving decomposition. Scalability remains topology-dependent: the technical report’s A.13, p. 23, reports 128-GPU A100 AllGather without NVLinks taking just over an hour versus ForestColl’s 20 seconds, at equal optimal bandwidth. This qualifies the headline synthesis-time claim.

The technical report’s AllReduce proof explicitly assumes symmetric links and GPU-only copying/reduction (A.9, pp. 19–21). Interpretation: its presented proof covers less hardware generality than the headline suggests.

Finite-chunk overhead is small when both the slowest link’s lifetime capacity and every tree’s assigned volume greatly exceed chunk size times route depth (§4.3). Small-message propagation delays, objectives beyond makespan, library integration, and end-to-end application validation remain open (§9, p. 12). SyCCL single-host cases and TACCL All-to-All are absent because of implementation limitations (§7).

### 7. Final assessment

Interpretation. OptCCL convincingly improves synthesis quality and scalability in its evaluated bandwidth-dominated settings. Its strongest contribution is separating routing from scheduling while retaining explicit feasibility checks. The weakest evidence concerns deployment: simulations do not establish real application gains. Optimality and scalability conclusions should retain the finite-chunk, hardware, and topology qualifications.

# Clear Research Trends in Today's Papers

## Restructure dependencies around hardware constraints

Interpretation. HipKittens and Presto both address dependencies that limit useful hardware concurrency. HipKittens alternates computation and loading across waves to accommodate AMD's static register allocation. Presto validates speculative state updates downstream and uses payload-free synthetic segments to complete backward updates through a forward-only pipeline. This pair suggests reorganizing work and state updates around hardware execution constraints. The trade-off is greater scheduling and correctness complexity: HipKittens requires architecture-specific tuning, and optional register pinning bypasses compiler safety guarantees. Presto's finite out-of-order tracking bounds reordering tolerance; omitted payload checksums and simulation-only selective-recovery evaluation leave protocol-completeness questions open.

Supporting papers: HipKittens: Fast and Furious AMD Kernels; Presto: A Match-Action TCP Stack for the Terabit Era.

## Coordinate communication across concurrent work

Interpretation. KUNSERVE and OptCCL address concurrent work competing for shared communication resources. After reclaiming replicated weights for KV-cache capacity, KUNSERVE chunks cache exchanges, prioritizes activation transfers, and balances pipeline microbatches using predicted execution costs. OptCCL jointly optimizes collective routes under shared bandwidth budgets, then schedules chunks to approximate the resulting rates. Together they suggest managing shared bandwidth and pipeline progress explicitly, although KUNSERVE targets serving latency and OptCCL targets collective completion time. The unresolved trade-off is aggregate efficiency versus sensitivity to timing: KUNSERVE's transitions typically pause affected requests for 1–2 seconds on its evaluated 200-Gbps network; OptCCL's guarantees assume bandwidth dominates, and real GPU application gains remain unvalidated.

Supporting papers: KUNSERVE: Parameter-centric Memory Management for Efficient Memory Overloading Handling in LLM Serving; OptCCL: Scalable Synthesis of Optimal Collective Communication Algorithms.
