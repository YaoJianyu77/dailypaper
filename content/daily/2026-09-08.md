## Latest papers 1 — Modular GPU Programming with Typed Perspectives

**PLDI · 2026-06-08 · Manya Bansal, Daniel Sainati, Joseph W. Cutler, Saman Amarasinghe, Jonathan Ragan-Kelley.** [Official publication](https://api.crossref.org/works/10.1145%2F3808290) · [Full paper](https://arxiv.org/pdf/2511.11939)

### 1. Paper in brief

Prism makes GPU collective operations composable by putting their thread requirements into types. CUDA functions can hide requirements that an aligned warp, warpgroup, or block cooperate, leaving callers to reconstruct those requirements from documentation. Prism instead tracks a program’s perspective on both computation and data, checks function interfaces, and inserts synchronization when memory changes hands. It retains explicit Tensor Core operations and asynchronous transfers, then erases perspective metadata when generating CUDA. In its square BF16 matrix-multiplication evaluation, the authors report H100 performance within 15% of cuBLAS. The contribution combines a language, compiler, and formal model; its safety guarantee does not establish race freedom or deadlock freedom. This analysis uses the supplied 48-page arXiv v1, including appendices.

### 2. Problem and core insight

The objective is modular kernel programming while preserving control over hardware operations and throughput. A collective requires the right participants and alignment: 32 consecutive threads starting at thread 1 cannot substitute for an aligned warp. Ordinary argument types do not communicate that constraint across function boundaries (pp. 3–4).

The first insight is to represent these requirements as perspectives: a hierarchy level plus a static size and alignment. A warp becomes `thread[32]`, and a warpgroup becomes `thread[128]`, allowing collective requirements to be checked compositionally (p. 7).

The second insight is that grouping code is insufficient if its data can make participants diverge. A variable’s perspective records where its value is uniform. Restricting information flow from broader to narrower perspectives prevents a per-thread flag from controlling a block-wide collective, while explicit resource splitting still permits deliberate divergence (pp. 8–9).

### 3. How the method works

Annotated Python-embedded kernels enter type checking, receive inferred synchronization, become CUDA, and pass through nvcc to executable kernels. At execution, preallocated global arrays supply inputs and receive outputs; perspectives themselves require no runtime checks (pp. 9, 15).

`group` replicates a narrower computation across available resources; same-level sizes must divide evenly. `split` assigns parallel branches separate, aligned resource subsets. Every split branch executes, unlike ordinary pattern matching. The contextual `id()` returns positions relative to the current grouping, so reusable functions need not reconstruct their location in the entire grid (pp. 7–10).

Code can read data uniform at its own or broader perspective and write values into variables at its own or narrower perspective. Shared/global pointers also have perspectives. `partition` temporarily hides a pointer and supplies narrower views through a programmer’s indexing function; `claim` gives access to one narrower collection and excludes sibling branches. Neither operation proves that arbitrary indices address distinct locations. Function signatures specify compute bounds, argument perspectives, and shared-memory requirements; mutable pointer perspectives must match, while const pointers may be broader. Shared-memory allocations have static sizes checked against declared budgets (pp. 9–11).

For memory reuse, the compiler builds a graph of partitions and their ordering, including loop backedges. A write before or after another access requires synchronization; consecutive reads do not. It emits barrier arrivals and waits, moving arrivals toward last use and waits toward first use to reduce unnecessary blocking. Asynchronous transfers receive corresponding completion synchronization (p. 15).

The H100 example connects these mechanisms: one producer warpgroup feeds Tensor Memory Accelerator (TMA) transfers into four separately named buffer slots; two consumer warpgroups issue asynchronous Tensor Core operations and write BF16 results. Its 384-thread kernel uses 128×256 output tiles, 64-element reduction tiles, BF16 operands, and FP32 accumulators. Naming slots separately enables independent dependency tracking, but forces static pipelines and unrolled load logic (p. 18; Appendix B.5, pp. 46–48).

### 5. Experimental evidence

Experiments use an NVIDIA H100 SXM5 and 4070 Ti Super, nvcc 12.3, random inputs, five warmup iterations, and ten measured iterations. Runtimes are averaged; aggregate comparisons use geometric means. The preprint prints the compiler flags as `-03 –use_fast_math` (pp. 2, 16).

Five FP32 GEMM implementations progressively introduce coalescing, shared-memory tiling, vectorization, and warp tiling. The best approaches cuBLAS on square matrices, supporting expressivity across granularities (Figure 21, p. 18). Exact aggregate ratio: Not specified in the paper.

Single-pass prefix scan achieves bandwidth within 7% of CUB for arrays exceeding L2 capacity. It combines local scans with inter-block look-back, whose global-memory coordination uses unsafe code (pp. 16–17, 19; Figure 22).

For square BF16 GEMM on H100, the authors report performance within 15% of cuBLAS. They attribute the remaining gap to an nvcc register-redistribution optimization failing to trigger with Prism’s pipeline structure. Interpretation: the experiment supports competitive performance, but no ablation independently isolates that explanation (p. 19).

### 6. Contributions and limitations

Prism contributes enforceable collective interfaces and automatic synchronization while retaining low-level control. Bundl supplies syntactic type-and-perspective safety through progress and preservation, assuming in-bounds accesses. It does not prove eventual collective participation, termination, non-interference, or deadlock freedom. Non-injective partitions can race (pp. 10, 14, 26, 30–35).

Pipelines require static, separately named slots. The supplied H100 listing lacks a general reduction-tail path, and scan coordination helpers appear as raw-CUDA stubs (pp. 44, 46–48). Library versions, timing API, numerical tolerances, and uncertainty intervals: Not specified in the paper.

Interpretation: checking an unsafe wrapper’s declared interface cannot validate arbitrary assembly inside it. The small benchmark suite and qualitative library example also leave productivity gains, bug reduction, and broader workload performance unmeasured.

### 7. Final assessment

Interpretation: Prism convincingly demonstrates a useful language and compiler design: collective requirements can become checkable interfaces without eliminating advanced GPU operations. Its strongest evidence combines a precise formal model with demanding kernels; its weakest part is the narrow evaluation and incomplete reproducibility detail. The results support competitive performance for the tested kernels and devices, with explicit limits on memory safety, liveness, and general-shape support.

## Latest papers 2 — SuperInfer: SLO-Aware Rotary Scheduling and Memory Management for LLM Inference on Superchips

**MLSys · 2026-05-18 · Jiahuan Yu, Mingtao Hu, Zichao Lin, Minjia Zhang.** [Official publication](https://proceedings.mlsys.org/paper_files/paper/2026/hash/07fd64f9316f40193c6a4d87d8afa011-Abstract-Conference.html) · [Full paper](https://proceedings.mlsys.org/paper_files/paper/2026/file/07fd64f9316f40193c6a4d87d8afa011-Paper-Conference.pdf)

### 1. Paper in brief

SuperInfer addresses a serving bottleneck that request reordering alone cannot solve: growing key–value (KV) caches fill GPU memory, preventing new prompts from starting. On NVIDIA GH200, plentiful CPU memory and NVLink-C2C make offloading attractive, but conventional transfers squander bandwidth. SuperInfer combines RotaSched, which rotates requests according to latency urgency, with DuplexKV, which reorganizes cache blocks and safely overlaps transfers in both directions. Its contribution is the joint design of scheduling and memory movement for time-to-first-token (TTFT) and time-between-tokens (TBT) service-level objectives (SLOs). A transfer microbenchmark takes 46.80 ms versus 1,556.15 ms with naive copying; serving tests improve first-token responsiveness, although inter-token performance does not dominate every baseline (Table 1; Figure 16).

### 2. Problem and core insight

The input is concurrent generation requests; the output is streamed tokens. The objective is to meet latency targets while retaining throughput despite finite high-bandwidth memory (HBM). Prioritizing new arrivals reduces TTFT but can strand offloaded requests; immediately resuming offloaded requests protects TBT while delaying arrivals (Figure 1, p. 3).

First, CPU capacity helps responsiveness only with rotation guided by both latency objectives. Second, rapid rotation requires transfer changes: fragmented, layer-oriented KV storage generates many small copies, while reusing outgoing HBM blocks for incoming data creates dependencies that serialize directions. RotaSched addresses urgency; DuplexKV addresses transfer granularity and safe block reuse (pp. 5–8).

### 3. How the method works

Requests enter a waiting queue → RotaSched selects work and allocates cache capacity → DuplexKV prepares resident KV blocks → GPU prefill/decoding produces tokens → completed requests leave, while paused requests await another rotation.

RotaSched maintains waiting, running, and rotary states; rotary means paused with KV stored in CPU DRAM. Waiting Virtual Lag Time (VLT) is time since arrival minus its tolerance, clipped at zero. Rotary VLT is time since the last generated token minus its tolerance, clipped at zero and multiplied by α. Entering rotary does not reset the last-token timestamp or guarantee zero lag. Running VLT negates elapsed time in the current running interval, favoring longer-running requests for preemption. Larger α favors rotary resumption over new arrivals (pp. 5–6, 10).

Each iteration uses first-come-first-served scheduling if memory suffices. Otherwise, Largest-VLT-First sorts requests, admits urgent waiting/rotary requests within free HBM plus a transfer budget, and preempts running requests from the opposite end until enough blocks become available (Algorithm 1, p. 7).

DuplexKV copies completed, immutable KV blocks to DRAM before preemption. Once a valid host copy exists, the HBM copy can be discarded safely; only the final, still-changing block requires copying at preemption. A block table tracks residency and synchronization. This removes dependencies for synchronized blocks without allocating duplicate HBM storage (Figure 13, p. 8).

A block-first layout places all layers of each block contiguously: Qwen2.5-32B’s 64 separate 64 KB segments become one 4 MB region. Modified PagedAttention kernels preserve paging with changed strides. `cudaMemcpyBatchAsync` batches transfers per direction, reducing launch overhead. Separate transfer streams and a pipeline across iterations overlap scheduling and transfers with GPU computation (pp. 8–9).

### 5. Experimental evidence

The GH200 NVL2 testbed provides 144 GB HBM and 480 GB DRAM per superchip; allocations use local NUMA placement, with 400 GB reserved for offloaded KV. SuperInfer builds on vLLM 0.6.6.post1, PyTorch 2.5.1, and CUDA 12.8. Models are LLaMA-3-8B, Qwen2.5-32B, and Mixtral-8x7B; datasets are ShareGPT and LMSYS-Chat-1M. Each trial samples 120 × requests-per-second requests; the authors describe Poisson-sampled interarrival delays. ShareGPT uses the first conversational turn. TTFT/TBT thresholds are 5 s/100 ms; α=3, βB=0, βF=0.5, and the transfer budget is 2,400 blocks (pp. 8–9, 18–19).

First, the paper specifies the vLLM baseline as 0.6.6.post1 with the V1 engine enabled (§5.2, p. 8), using PyTorch 2.5.1 (p. 18). Figure 16 also compares TensorRT-LLM 1.1.0, LightLLM, LTR, and NEO; all baselines enable PagedAttention and chunked prefill. NEO lacks Mixtral support. SuperInfer improves TTFT attainment under high load, but TensorRT-LLM achieves higher TBT attainment in several panels. The abstract reports a maximum 74.7% TTFT-attainment improvement; its exact comparator/operating point and relative-percent versus percentage-point meaning: Not specified in the paper.

Third, the Qwen/ShareGPT ablation shows that increasing the transfer budget from 300 to 2,400 with the original engine harms TBT, whereas DuplexKV supports the larger budget (Figure 17). Across the main experiments, incomplete overlap stalls only 0.021% of iterations; average scheduling/transfer/model times are 7.63/15.8/69.82 ms (p. 11).

### 6. Contributions and limitations

The conceptual contribution is proactive rotation according to SLO progress; the engineering contribution is synchronization-aware offloading integrated with cache layout and batching. Benefits target memory contention; the authors report baseline-like behavior when memory suffices. Parameter tuning trades TTFT against TBT rather than guaranteeing either. Page 6 inconsistently assigns SLO symbols relative to its equations and later discussion.

Model/KV precision, prompt/output length distributions, batching limits, and the aggregation used for per-request TBT attainment: Not specified in the paper. Pie is excluded because code was unavailable. Distributed evidence covers only two GPUs (TP=2). Interpretation. The evidence therefore supports this GH200 setup more strongly than larger deployments or different interconnects. Appendix D’s poor unified-memory result concerns its tested configuration, not every possible memory-placement policy.

### 7. Final assessment

Interpretation. SuperInfer demonstrates that proactive scheduling benefits from cache movement engineered to match it. Transfer measurements and ablation provide the strongest causal evidence; incomplete workload/metric details and limited deployment breadth are weaknesses. The contribution combines latency priorities with efficient memory movement. Conclusions are strongest for memory-constrained GH200 serving under evaluated workloads, without implying universal TBT superiority or hard SLO guarantees.

## Latest papers 3 — DynaFlow: Transparent and Flexible Intra-Device Parallelism via Programmable Operator Scheduling

**MLSys · 2026-05-18 · Yi Pan, Yile Gu, Jinbin Luo, Yibo Wu, Ziren Wang, Hongtao Zhang, Ziyi Xu, Shengkai Lin, Baris Kasikci, Stephanie Wang.** [Official publication](https://proceedings.mlsys.org/paper_files/paper/2026/hash/bbd7d8bd780fcf7143add2317ba04638-Abstract-Conference.html) · [Full paper (1/2)](https://proceedings.mlsys.org/paper_files/paper/2026/file/bbd7d8bd780fcf7143add2317ba04638-Paper-Conference.pdf) · [Full paper (2/2)](https://proceedings.mlsys.org/paper_files/paper/2026/file/bbd7d8bd780fcf7143add2317ba04638-Supplemental-Conference.pdf)

### 1. Paper in brief

DynaFlow addresses idle GPU resources during distributed ML inference and training, where computation, memory access, and communication run sequentially despite opportunities to overlap. Existing frameworks entangle operator order with model code, making alternative schedules expensive to integrate and adapt. DynaFlow separates the model graph from a programmable Python scheduler: developers annotate schedulable subgraphs, then selectively split batches, overlap work, or substitute fused kernels. An asynchronous backend handles dependencies and tensor storage while retaining subgraph-level CUDA Graphs and TorchInductor compilation. Across six framework integrations, the main evaluation reports throughput gains up to 1.29× over original systems. Its contribution is a reusable scheduling interface and supporting runtime; benefits depend on workload, kernels, and hardware, and dynamic scheduling introduces measurable overhead (§§3–5).

### 2. Problem and core insight

The input is an existing PyTorch model and its execution batches; the objective is higher throughput while respecting graph dependencies. Matrix multiplication, attention, normalization, and collectives stress different resources. Overlap can exploit their complementary demands, but splitting small batches adds weight reads, while concurrent kernels can contend for GPU resources (§2).

Two observations drive the design. First, useful scheduling boundaries usually match logical operations such as attention, rather than individual tensor instructions; annotations therefore expose meaningful work without overwhelming the scheduler. Second, global execution order may vary while local computation remains reusable. DynaFlow consequently combines dynamic orchestration with statically optimized subgraphs, using managed buffers to avoid copies when their batch partitions differ (§3, pp. 5–7).

### 3. How the method works

Model and batch → graph tracing and partitioning → scheduling and asynchronous execution → model outputs. Implemented as a `torch.compile` backend, DynaFlow intercepts execution after TorchDynamo captures the graph. Developers identify boundaries by module type, function pattern, or marked code region, then supply the scheduling policy (§§3–4).

The scheduler calls `split` to establish logical micro-batches, `get_ready_ops` to retrieve eligible subgraphs, and `execute` to dispatch them onto chosen streams. Dispatching corresponding operators together merges micro-batches for that operation; `replace_func` substitutes a developer-provided fused kernel. Dual-batch overlap, for example, retains full-batch attention but divides mixture-of-experts computation into two micro-batches, overlapping expert dispatch/combine communication with computation. The scheduler can disable splitting for small batches (§3.2).

The callback-driven engine consumes dispatch requests, updates dependency state, and returns newly eligible subgraphs. Static analysis records tensor reference counts and identifies future merge inputs. Runtime hooks direct producer outputs into slices of preallocated contiguous buffers, allowing consumers to access combined data without concatenation copies; reference counts manage tensor lifetimes (Algorithm 1).

TorchInductor compiles each subgraph for reuse. CUDA Graphs are captured separately per subgraph and micro-batch to keep concurrent data separate, with a shared memory pool across subgraphs and batch sizes within each micro-batch. This preserves launch optimizations while increasing capture/storage requirements (§3.3).

### 5. Experimental evidence

The testbeds are eight NVLink-connected B200 GPUs and four NVLink-connected H100 GPUs. H100 handles Transformers, xDiT, FastVideo, Flux, and Comet experiments. Software is PyTorch 2.8.0, CUDA 12.8, and driver 580, except Comet uses PyTorch 2.6.0/CUDA 12.4. Workloads include fixed token lengths, ShareGPT, LMSYS-Chat-1M, and Splitwise (§5.1).

First, NanoFlow integration improves offline vLLM throughput by up to 1.17× for Llama-3-8B on two B200 GPUs, and 1.29× for both Llama-3-70B and Qwen-2.5-72B on eight. The larger-model maxima occur at 2,048 input/128 output tokens. TorchInductor was disabled because the naive integration lacked support. Synthetic 512/128 traffic allowed splitting in 91.71% of iterations, versus 46.21% on ShareGPT, supporting the workload-sensitivity explanation (§5.3.1, pp. 9–10).

Second, supplementary DBO experiments use DeepSeek-V2-Lite with two-GPU expert parallelism and `NCCL_P2P_DISABLE=1`, forcing communication over PCIe. On Splitwise, DynaFlow reaches 2.06× baseline vLLM throughput; native DBO reaches 1.30× on that same workload. This demonstrates benefit under constrained communication, but is a single-node proxy, not a multi-node evaluation (Appendix B, combined p. 16).

Third, the Llama-3-8B/ShareGPT ablation on two B200 GPUs gives 1.14× throughput with all optimizations and 1.10× without zero-copy preallocation, relative to CUDA-Graph-enabled vLLM. This isolates a modest memory-management contribution (§5.5; Figure 14).

### 6. Contributions and limitations

The contribution is compiler/runtime integration across vLLM, SGLang, Megatron-LM, Transformers, xDiT, and FastVideo. Developers still choose partitions, policies, and replacement kernels. Megatron's custom backward operator limits graph capture; attention-heavy long videos leave little communication to hide (§5.3.3). The Flux-style integration actually loses up to 20% throughput: its replacement kernel was slower (§5.3.5).

Costs remain measurable. Batch-one Llama-3-8B CPU launch time is 10.8 ms with dynamic scheduling, versus 4.4 ms for vLLM and 4.7 ms for sequential fallback. At maximum capture batch 512, graph memory rises from 0.98 to 1.80 GiB (§§5.2.2, 5.4).

The supplement specifies PyTorch 2.10+ for `mark` (combined p. 16).

Evidence has inconsistencies: Figure 14 labels no-graph/static scheduling as 1.00×/0.94×, whereas prose says 0.96×/1.00×; SGLang maxima also differ between Figure 9 and prose. Those disputed values are excluded from conclusions. Tail-latency guarantees and numerical-equivalence testing: Not specified in the paper. Interpretation. Throughput evidence does not establish latency-sensitive serving benefits.

### 7. Final assessment

DynaFlow convincingly demonstrates that programmable scheduling can reuse existing model implementations while retaining useful low-level optimizations. Its strongest evidence combines framework integration, conditioned vLLM throughput gains, and zero-copy ablation. The weakest areas are inconsistent reported measurements and limited deployment coverage. The main contribution is a scheduling abstraction backed by runtime engineering; its conclusions are strongest for the evaluated offline workloads with enough work or communication to hide overhead.

## Latest papers 4 — Flashlight: PyTorch Compiler Extensions to Accelerate Attention Variants

**MLSys · 2026-05-18 · Bozhi You, Irene Wang, Zelal Su Mustafaoglu, Abhinav Jangda, Angélica Moreira, Roshan Dathathri, Divya Mahajan, Keshav Pingali.** [Official publication](https://proceedings.mlsys.org/paper_files/paper/2026/hash/bc52716d13d2d72ea0f335667d86c0f8-Abstract-Conference.html) · [Full paper (1/2)](https://proceedings.mlsys.org/paper_files/paper/2026/file/bc52716d13d2d72ea0f335667d86c0f8-Paper-Conference.pdf) · [Full paper (2/2)](https://arxiv.org/pdf/2511.02043)

### 1. Paper in brief

Flashlight extends TorchInductor to generate fused attention kernels directly from ordinary PyTorch programs. Existing compilation often separates matrix multiplications from reductions, materializing large intermediates; FlexAttention permits customization within a prescribed attention template. Flashlight instead represents contractions and reductions together, changes loop structure, and converts compatible dependent reductions into online computations. This enables tiling and fusion across differential attention and Evoformer attention, alongside conventional variants. In OpenFold’s AlphaFold2 implementation, compiling gated attention with Flashlight reduces complete inference latency by 6–9% on A100 and H100 GPUs (§4.4). Its contribution is compiler expressiveness with practical acceleration. Performance remains conditional: cached sparse attention favors FlexAttention, specialized FlashInfer usually wins supported variants, and plotted differential-attention results include regressions.

### 2. Problem and core insight

The input is an attention program over queries, keys, values, and variant-specific operations; the output is the corresponding attention tensor. The objective is lower runtime and memory traffic without rewriting models into kernel templates. Ordinary attention materializes a sequence-length-squared score matrix when fusion fails (§2.2).

Two observations drive the design. First, matrix multiplication is a reduction with parallel output dimensions. Giving it the same intermediate representation as other operators removes an artificial fusion boundary; moving selected parallel work inside a consumer trades parallelism for locality (§§3.1–3.2). Second, dependence on a completed reduction can sometimes be replaced by corrected running state. Algebraic identities therefore enable fusion that matching loop shapes alone cannot justify (§§3.3–3.4).

### 3. How the method works

PyTorch code → graph capture → unified reduction representation → structural and algebraic fusion → tiled Triton kernels → attention output. Examples enable Flashlight through `torch.compile` with `dynamic=False` (§3).

The representation separates independent parallel dimensions from reduction dimensions. For a score producer followed by a row reduction, dimension demotion moves the producer’s column dimension into the fused kernel’s inner loop. A block produces and consumes intermediate tiles locally, avoiding global-memory writes and subsequent reads, but exposing less independent GPU work (§3.2).

Softmax needs additional reasoning: its exponential sum normally waits for the final row maximum. Flashlight maintains running maximum m and denominator d. For a new score x, m′ = max(m,x) and d′ = d·exp(m−m′) + exp(x−m′). Rescaling preserves prior contributions when the maximum changes, allowing an online pass. Algorithm 2 and Appendix A supply the recurrence and real-arithmetic justification (pp. 2, 16–17).

To fuse successive matrix multiplications, a small consumer output dimension can fit entirely within one tile. Removing its single-iteration tile loop makes the remaining producer/consumer dimensions compatible. Logical tile coordinates are flattened onto one physical GPU grid dimension, retaining independent tile-size choices (§§3.5–3.6).

Generated attention computes score tiles, applies online normalization, and accumulates products with value tiles without storing the full attention matrix. Autotuning selects blocks, warps, and pipeline stages; block ordering improves L2 reuse. FP16/BF16 contractions accumulate in FP32 while preserving output precision (§3.7).

### 5. Experimental evidence

Experiments use 80-GB H100/A100 GPUs capped at 1290/1080 MHz, Python 3.12, PyTorch 2.5.0, Triton 3.1.0, CUDA 12.9, and FlashInfer 0.2.5. Kernel measurements average 20 runs after 10 warmups (§4.1). Benchmark input dtype: **Not specified in the paper.**

**Supported variants.** Seven variants cover ordinary attention, ALiBi, Softcap, causal, sliding-window, prefix, and document masks. Sequence lengths span 512–16,384 with batch×length fixed at 16,384; head dimension is 64. Multi-head attention uses 16 heads; grouped-query attention uses 16 query and two key/value heads. Window/prefix lengths are 256; document count is 12. Figure 2 labels Softcap grouped-query attention at batch 4, length 4096 as 1.49× faster than FlexAttention on H100. Sparse FlexAttention kernels run faster, but mask construction can reverse the comparison. FlashInfer usually beats both, except ALiBi (§4.2).

**Complex attention and AlphaFold2.** Figure 4’s Evoformer speedups span 4.37–7.93× over its baseline, labeled “torch” and identified as `torch.compile` in §4.3: four heads, dimensions 64/128, two sequence dimensions of 256, batches 1–32. This contradicts §4.3’s blanket ≥5× statement. Differential attention with 16 heads, dimension 128, batch 1, length 16,384 shows 0.79×/0.98× on H100/A100, contradicting “always faster.” Separately, OpenFold’s 48-layer Evoformer configuration uses eight heads of dimension 32, invariant-point attention uses 12 of dimension 16, sequence dimensions are 256, and batches span 1–32. Compiling row/column gated attention reduces whole-model latency 6–9%; ordinary compilation provides negligible improvement (§4.4).

**Serving.** Modified LLaMa-3.2-1B runs the first 200 Mooncake requests on H100 after replay warmup. Figure 5 reports Softcap latency speedups of 1.17× for P99 time to first token and 1.05× for P99 inter-token latency, with 1.04× throughput. Causal ratios are 0.78×, 0.80×, and 0.87× respectively: FlexAttention wins as mask preparation is amortized. Unfused PyTorch/compiler baselines exhaust memory (§4.4).

### 6. Contributions and limitations

The contribution combines reusable compiler transformations with TorchInductor integration. Evaluation covers inference; training and block-sparsity optimization remain future work. Reduced parallelism can hurt performance, and real-number equivalence does not guarantee floating-point equivalence (§3.8). Numerical-error measurements and per-pass ablations: **Not specified in the paper.** **Interpretation.** Aggregate timings cannot isolate each transformation’s contribution or establish arbitrary-program coverage.

The author version retains the main results and adds Appendix C (combined pp. 35, 37–39): a monkey patch over stock PyTorch, synthetic random kernel inputs, vLLM 0.6.6, and compilation/autotuning taking up to several minutes. Its reproduction workflow may substitute stored Figure 4 data for the unavailable GPU and approximate clock capping through warmup. These details qualify reproduction; they are not additional fresh measurements.

### 7. Final assessment

Flashlight convincingly demonstrates that a general compiler can recover useful attention fusion from ordinary model code, including compositions outside FlexAttention’s template. Its strongest evidence combines substantial Evoformer acceleration with a smaller complete-model gain. Broad performance claims are weakened by plotted regressions and sparse-kernel advantages. The results best support warmed inference on the evaluated GPUs and shapes; numerical robustness, training, and benefits beyond those workloads remain uncertain.

# Clear Research Trends in Today's Papers

## Explicit execution structure makes GPU optimization more reusable

Interpretation. Today's selected papers show a shared response to GPU optimizations that are difficult to compose or adapt: expose the execution structure through programming interfaces and compiler representations. Modular GPU Programming with Typed Perspectives (Prism) encodes collective participation and data uniformity; DynaFlow exposes schedulable subgraphs; Flashlight represents contractions and reductions together to enable fusion. These approaches make advanced optimizations accessible through reusable abstractions. The unresolved trade-off is how much flexibility and automation they can provide while preserving correctness and efficiency. Prism does not establish race or deadlock freedom, DynaFlow adds scheduling and CUDA Graph memory costs, and Flashlight's transformations can reduce parallelism and regress on some workloads.

Supporting papers: Modular GPU Programming with Typed Perspectives; DynaFlow: Transparent and Flexible Intra-Device Parallelism via Programmable Operator Scheduling; Flashlight: PyTorch Compiler Extensions to Accelerate Attention Variants.

## Useful overlap requires coordinated scheduling and data movement

Interpretation. SuperInfer and DynaFlow show that opportunities for concurrency can remain unusable when data movement and buffer dependencies serialize execution. SuperInfer couples latency-guided request rotation with proactive KV-cache copies, contiguous block layouts, and concurrent transfers. DynaFlow couples programmable operator schedules with dependency tracking and preallocated buffers that avoid concatenation copies. Together, they support designing scheduling, data layout, and buffer lifetimes as one system. The unresolved trade-off is whether the resulting overlap outweighs transfer costs, resource contention, scheduling overhead, and memory consumption. Their objectives also differ: SuperInfer balances first-token and inter-token latency without hard guarantees, while DynaFlow primarily establishes throughput benefits and leaves latency-sensitive serving benefits unproven.

Supporting papers: SuperInfer: SLO-Aware Rotary Scheduling and Memory Management for LLM Inference on Superchips; DynaFlow: Transparent and Flexible Intra-Device Parallelism via Programmable Operator Scheduling.
