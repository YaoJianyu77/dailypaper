### 1. MPK: A Compiler and Runtime for Mega-Kernelizing Tensor Programs

**论文信息。** 中文可译为“面向张量程序巨型内核化的编译器与运行时”。主要作者 Xinhao Cheng、Zhihao Zhang、Yu Zhou、Jianan Ji 等；OSDI 2026，正式公开日期 2026-07-13，pp. 1909–1926；arXiv:2512.22219。预印本旧题 *Mirage Persistent Kernel: A Compiler and Runtime for Mega-Kernelizing Tensor Programs*，与正式版是同一工作。[官方论文页](https://www.usenix.org/conference/osdi26/presentation/cheng)｜[全文 PDF](https://www.usenix.org/system/files/osdi26-cheng.pdf)｜[代码](https://github.com/mirage-project/mirage)。**阅读依据：已读取全文并逐页核对关键图表。**

**30 秒速览。** 传统“一个算子一个 kernel”把算子边界变成全局屏障，既产生大量 launch 开销，也挡住跨算子流水及计算—通信重叠。MPK 把整段推理编译为 SM 粒度任务图，并由单个 persistent mega-kernel 在 GPU 内调度；A100/H100/B200 上相对现有服务系统达到 1.0–1.7× 性能，价值在于把全模型融合从手工技巧提升为编译器与运行时问题。

**技术解读。** 瓶颈是 operator DAG 只表达张量依赖，粒度粗到无法说明某个 SM 上的子任务何时可执行。MPK 的关键观察是：若把节点降为单个 SM 执行的 task，把边表达为 event，就能显式暴露局部就绪关系。编译器把 tensor program、batch 配置和 GPU 架构降为 **tGraph＝SM 级任务／事件图**，再做 event fusion、normalization 和 linearization，分别减少同步、规整依赖并压缩运行时状态；每个 task 被生成 CUDA device function。运行时把 SM 划为 scheduler 与 FIFO worker，按事件就绪异步派发，并混合 AOT 预排队与 JIT 动态派发；动态 batch 则预编译若干 2 的幂规模 tGraph 后在运行时选择。这样 MatMul、collective、分页共享内存和请求调度都能留在同一 kernel 内跨边界流水，而非等待整个前一算子结束。

**关键实验与图表。** Figure 4（PDF 第 5 页）展示 computation graph→tGraph→单 mega-kernel 的完整链路；Figure 9（PDF 第 12 页）在 A100、H100、B200 上比较五个 dense/MoE 模型，batch 1–16 时相对 vLLM/SGLang 最佳基线为 1.0–1.7×；Figure 11（第 13 页）在 8×H100 tensor parallel 下对 vLLM/SGLang 为 1.1–1.4×，对原生 PyTorch 最高超过 10×。Table 2（第 14 页）显示 event fusion 将事件数减少 37–118×，linearization 将图状态占用压缩 4.4–15×；这些是特定模型、硬件和配置的结果，不能外推到所有 GPU 程序。

**局限与关联。** 作者实验主要是固定 prompt=64、output=1024、greedy decoding 的 offline batching，并未证明真实在线到达、租户公平性或尾延迟 SLO；每线程寄存器还按所有 task 的最大需求静态占用，新 GPU 也需要新的 task codegen。它直接对应 GPU kernel 优化、并发执行和计算通信重叠，但收益依赖模型形状与硬件专门化。

### 2. Prism: Cost-Efficient Multi-LLM Serving via GPU Memory Ballooning

**论文信息。** 中文可译为“以 GPU 内存气球机制实现低成本多 LLM 服务”。主要作者 Shan Yu、Yifan Qiao、Mingyuan Ma、Yangmin Li、Shuo Yang 等；OSDI 2026，正式公开日期 2026-07-13，pp. 75–93；arXiv:2505.04021。预印本旧题 *Prism: Unleashing GPU Sharing for Cost-Efficient Multi-LLM Serving*，与正式版是同一工作。[官方论文页](https://www.usenix.org/conference/osdi26/presentation/yu-shan)｜[全文 PDF](https://www.usenix.org/system/files/osdi26-yu-shan.pdf)｜[研究代码](https://github.com/Multi-LLM/prism-research)｜[kvcached](https://github.com/ovg-project/kvcached)。**阅读依据：已读取全文并逐页核对关键图表。**

**30 秒速览。** 多模型提供商既要让长尾模型随时可用，又面对活跃模型组合快速变化；固定空间切分会排队，纯时间共享又会换模抖动。Prism 用 GPU memory ballooning 动态回收、映射和重分配跨模型显存，再以全局放置和本地 slack 调度统一空间／时间共享。真实轨迹中，它用相同 GPU 将 TTFT SLO 达成率最多提高 3.3×，或把成本降低超过 2×。

**技术解读。** 核心观察是模型的权重与 KV cache 并非必须绑定固定物理显存。**Memory ballooning＝先保留较大的虚拟地址区，再按需映射或回收物理页**；Prism 的 kvcached 以 2 MB 粒度在模型之间重分配内存，映射开销为毫秒级且无需改 attention kernel。全局层根据各模型的 KV pressure ratio 做 demand-complementary placement，尽量把峰值错开的模型放在一起；每个 GPU 的本地仲裁器再用请求 slack 决定 admission 与 batch，使急迫请求先获得显存和计算。Figure 3（PDF 第 7 页）把前端、GPU group、load-aware placement、balloon driver 与 slack-aware arbitration 串起来：显存弹性决定能否空间共享，模型激活决定何时退回时间共享，二者不再是静态二选一。

**关键实验与图表。** Table 1（PDF 第 4 页）涵盖 Hyperbolic、Novita、Arena-Battle、Arena-Chat 四条真实轨迹，共 16–129 个模型；许多模型变异系数大于 1，且每小时有 40–100 个空闲区间。Figure 5（第 12 页）在 2 GPU、8 模型下，Hyperbolic 轨迹达到 99% TTFT SLO 时承载量是 MuxServe++ 的 2.3×、静态分区的 3.5×；Arena-Chat 中超过各基线 3×。Figure 9（第 14 页）把 58 模型扩大到 32 GPU：Prism 用 16 GPU 已接近 99% TTFT，MuxServe++ 需 32 GPU。作者还报告 kvcached 已部署到 10K+ GPU；这是采用证据，不等于所有实验都来自生产集群。

**局限与关联。** 收益依赖多模型负载存在可利用的 burst/idle 互补；恒定负载消融中 ballooning 带来约 3–4 ms 开销，TPOT 相对开销最高 13%。Figure 10（第 14 页）显示 14B 模型激活约 1.3 s、70B 以上约 1.5 s，紧 TTFT 下未必可隐藏。它与显存管理、资源调度和多租户推理直接相关，主要权衡是弹性利用率与迁移／映射可预测性。

### 3. JITServe: SLO-aware LLM Serving with Imprecise Request Information

**论文信息。** 中文可译为“面向不精确请求信息的 SLO 感知 LLM 服务”。作者 Wei Zhang、Zhiyu Wu、Yi Mu、Rui Ning、Banruo Liu、Nikhil Sarda、Myungjin Lee、Fan Lai；NSDI 2026，正式公开日期 2026-05-04，pp. 825–848；DOI: 10.5555/3833220.3833264，arXiv:2504.20068。v1 旧题 *Tempo: Application-aware LLM Serving with Mixed SLO Requirements*，与正式版是同一工作。[官方论文页](https://www.usenix.org/conference/nsdi26/presentation/zhang-wei)｜[全文 PDF](https://www.usenix.org/system/files/nsdi26-zhang-wei.pdf)｜[代码](https://github.com/UIUC-MLSys/JITServe)。**阅读依据：已读取全文并逐页核对关键图表。**

**30 秒速览。** LLM 请求的输出长度与应用依赖往往事前未知，而不同应用又约束 TTFT/TBT、完成期限或整条 DAG；按单一吞吐指标排队会让很多已计算 token 仍错过 SLO。JITServe 先用高分位上界保守估计，再随生成逐步修正，并只给请求满足 SLO 所需的“刚好够用”带宽。16×A100 实验中服务 goodput 提升 1.4–6.3×，等效资源节省 28.5%–83.2%。

**技术解读。** **Service goodput＝在各自期限内交付、因而真正有用的 token 或请求量**。JITServe 的 request analyzer 用 Quantile Regression Forest 预测输出长度上界，并每生成 50 token 重估一次；依赖未知时用 pattern graph 匹配运行中逐渐显露的 DAG。调度核心 GMAX 先从剩余 token 和剩余时间计算每个请求的最低带宽与 margin，再以“单位带宽可带来的 goodput”排序；滑动窗口从输入长度相近的请求中选 batch，避免异质 batch 拉低效率。只有收益超过 KV reload／recompute 代价才抢占，并把决策按约 50 decode step（约 300 ms）分帧。算法复杂度 O(N log N)，论文给出相对离线最优至少 1/8.56 的理论保证。

**关键实验与图表。** Figure 4（PDF 第 6 页）展示 analyzer→GMAX→preemption 的闭环；Figure 5（同页）核验高分位长度预测与约 7 ms 推断开销；Figure 10（第 8 页）给出 grouped margin 调度。实验覆盖 Llama/Qwen、8B–70B、Alpaca/LMSys、数学、deep-research 与 agent-code 工作负载，基线含 vLLM、Sarathi-Serve、Autellix、LTR、SLOs-Serve。正文主结果中请求 goodput 相对 LTR 为 2.3–4.5×；多模型场景 Figure 18 为 1.34–2.42×，不同 SLO 混合 Figure 20 仍显示稳定收益。上述是作者设定 SLO 和到达轨迹下的结果，不代表任意服务策略都能节省 83.2% GPU。

**局限与关联。** 作者指出 all-or-nothing goodput 会把“只差一点”的请求计为零，可能诱发边界效应；分布漂移或应用图模式不匹配时需重训或 fallback。当前也未在线 profile GPU，异构 GPU／多节点部署可能需要选择性 profiling。论文直接连接请求调度、并发执行与应用级 SLO，关键代价是预测保守度、调度开销和公平性之间的取舍。

### 4. Octopus: Enhancing CXL Memory Pods via Sparse Topology

**论文信息。** 中文可译为“以稀疏拓扑增强 CXL 内存舱”。作者 Yuhong Zhong、Fiodar Kazhamiaka、Pantea Zardoshti、Shuwei Teng、Rodrigo Fonseca、Mark D. Hill、Daniel S. Berger；NSDI 2026，正式公开日期 2026-05-04，pp. 1303–1322；arXiv:2501.09020，DBLP: conf/nsdi/ZhongKZTFHB26。早期预印本题为 *Octopus: Scalable Low-Cost CXL Memory Pooling*，与正式版是同一工作。[官方论文页](https://www.usenix.org/conference/nsdi26/presentation/zhong)｜[全文 PDF](https://www.usenix.org/system/files/nsdi26-zhong.pdf)｜[代码与成本模型](https://github.com/yuhong-zhong/Octopus-CXL-Pod)。**阅读依据：已读取全文并逐页核对关键图表。**

**30 秒速览。** CXL 可以跨服务器池化内存，但全连接 multi-headed device（MPD）受端口数限制，CXL switch 又贵且增加延迟。Octopus 用稀疏 server–MPD 二部图，把 16 台服务器组成低延迟 island，再用跨 island MPD 扩大池化范围。三机原型加 96 机仿真表明，64-byte RPC 中位延迟为 1.2 μs，且同等约 16% 内存节省下设备成本低于交换式方案。

**技术解读。** 低延迟通信希望任意两台服务器共享某个 MPD，而内存池化希望热点服务器连接尽量不同的设备；完全重叠和完全分散都只优化一端。Octopus 采用 **BIBD＝平衡不完全区组设计** 安排 island 内端口，保证任意服务器对至少共享一个 MPD；剩余端口连接跨 island MPD，让过量内存需求分散到更大设备集合。Figure 1（PDF 第 2 页）并列全连接 MPD、switch 与 6-island/96-server Octopus：岛内边承担低延迟通信，岛外边扩大 pooling reach。系统还将 Azure VM 内存需求轨迹映射到拓扑，并用实测的 CXL 访问参数驱动放置与成本模型，因此贡献不只是画一张图，而是把物理端口、铜缆距离、设备价格、延迟与调度共同纳入设计。

**关键实验与图表。** 原型使用 3 台 AMD EPYC 9825 和 3 个预生产双端口 ×8 CXL 2.0 MPD。Figures 10–12（PDF 第 10 页）中 64-byte RPC 中位数 1.2 μs，比 CXL switch 低 2.4×、比机架内 RDMA 的 3.8 μs 低 3.2×；100 MB 按值传递为 5.1 ms，RDMA 高 3.3×；约 65% 测试应用在 MPD 内存上相对本地 DRAM 慢不到 10%。Table 5（第 12 页）显示 Octopus-96 与 90-server switch topology 都节省约 16% 内存容量，但 CXL 设备成本分别约 1,548 与 3,460 美元／server；整机 CapEx 结论依赖论文价格假设。

**局限与关联。** 96-server 结果来自仿真，真实硬件只有 3 server；跨 island 通信要经过两跳 MPD，broadcast/all-gather 需要复制或多跳。CXL 2.x 还缺少跨服务器硬件访问控制，链路 surprise removal 可能触发重启。它把内存池化、网络拓扑与资源调度连成一个系统问题，对 GPU pod、分离式内存和通信拓扑同样有方法论价值。

### 5. Efficient Memory Management for Large Language Model Serving with PagedAttention

**论文信息。** 中文可译为“用 PagedAttention 高效管理大模型服务内存”。主要作者 Woosuk Kwon、Zhuohan Li、Siyuan Zhuang、Ying Sheng 等；SOSP 2023，正式发表日期 2023-10-23，pp. 611–626；DOI: 10.1145/3600006.3613165，arXiv:2309.06180。[ACM 官方页](https://dl.acm.org/doi/10.1145/3600006.3613165)｜[全文 PDF](https://arxiv.org/pdf/2309.06180)｜[vLLM 代码](https://github.com/vllm-project/vllm)。**阅读依据：已读取全文并逐页核对关键图表。**

**代表性依据。** 这篇不是因“旧”或引用数入选：后续 OSDI 2024 的 [DistServe](https://www.usenix.org/system/files/osdi24-zhong-yinmin.pdf) 把 vLLM 作为广泛使用的主基线，ASPLOS 2025 的 [vAttention](https://arxiv.org/pdf/2405.04437) 直接以 PagedAttention 为对照，并指出相同抽象已进入 TensorRT-LLM、Hugging Face TGI、LightLLM 等服务栈；[vLLM 官方 2024 回顾](https://vllm.ai/blog/2025-01-10-vllm-2024-wrapped-2025-vision)还给出 Amazon Rufus、LinkedIn 等生产采用案例。今天的 MPK 与 JITServe 都直接比较或集成 vLLM，Prism 则把按页弹性进一步扩展到跨模型显存。因此持续影响来自后续顶会基线和实际系统采用，而非个人印象。

**30 秒速览。** 自回归输出长度未知，连续预留 KV cache 会产生内部／外部碎片，也难以在 parallel sampling 和 beam search 间共享前缀。PagedAttention 借鉴操作系统分页，把 KV 切成固定逻辑块，经 block table 映射到不连续物理块并按需分配；vLLM 因此在等延迟下通常达到既有系统 2–4× 吞吐，并把“KV 内存虚拟化”变成现代 LLM serving 的基础抽象。

**技术解读。** 传统引擎要求每个请求的 KV 连续，调度器只能按最大长度预留；Figure 2（PDF 第 2 页）显示真正 token state 仅占分配 KV 的 20.4%–38.2%。PagedAttention 的 **logical block＝序列看到的固定 token 块**，**physical block＝GPU 中任意可用的实际存储块**；中心 scheduler／block manager 维护 block table，token 到达时才分配。并行采样和 beam search 对共享 prompt block 增加引用计数，写入时 copy-on-write，避免整段复制；显存不足时可选择 swap 或 recompute。GPU worker 通过定制的 fused reshape/write 与 block-read attention kernel 读取非连续 KV。默认 block size 16，是 kernel 并行度、碎片和共享机会之间的实测折中。

**关键实验与图表。** Figure 4（PDF 第 5 页）给出 scheduler、KV manager、block table 与 worker；Figure 12（第 10 页）在 A100、OPT-13B/66B/175B 与 LLaMA-13B、ShareGPT/Alpaca 上比较 FasterTransformer 和作者重实现的 Orca，等延迟下 vLLM 通常为 2–4×，特定组合更高。Figure 13（同页）以 OPT-13B 解释来源：ShareGPT 平均 batch 从 Orca Max 的 7 提升到 30.42，Alpaca 从 7 提升到 132.44。Figure 15（第 11 页）显示 beam search 共享块节省 37.6%–66.3% 内存；数字均受模型、序列分布和作者基线实现限制。

**局限与关联。** Figure 18（PDF 第 12 页）表明 block-table lookup、分支和变长序列使其 attention kernel 比 FasterTransformer 慢 20%–26%；短序列、算力瓶颈场景中容量优势会缩小。实验到达是合成 Poisson，Orca 因无公开代码由作者重实现。它与操作系统虚拟内存的对应关系非常直接，也解释了 Prism 为何把按页弹性从单模型 KV 扩展到跨模型 GPU memory、Octopus 又如何在机间层次继续讨论池化拓扑。

## 今日论文中的明显研究趋势

1. **共同问题：粗粒度边界隐藏可调度空间。** MPK 把 operator 降为 SM task/event，JITServe 把“一个请求一个优先级”细化为随剩余时间变化的最低带宽，Prism 则把模型独占显存细化为 2 MB 物理页。今日选文呈现的方向是用更小、可重排的执行或资源单元打破静态边界；尚未解决的权衡是元数据与控制器开销、调度公平性，以及对特定 GPU 架构的专门化。

2. **共同问题：稀缺内存既要隔离又要池化。** Prism 用虚拟—物理映射在模型间弹性回收 GPU 显存，Octopus 用稀疏 CXL 拓扑在服务器间扩大 pooling reach；PagedAttention 提供了单模型内部的历史起点。方向从“预留连续容量”转向多层 indirection 与按需绑定；代价仍是映射／迁移延迟、故障隔离、跨域带宽和真实性能能否在大规模硬件上兑现。

3. **共同问题：平均吞吐不能代表服务价值。** Prism 面向会漂移的 bursty-group 轨迹最大化 SLO attainment，JITServe 面向未知输出和应用 DAG 最大化 service goodput；二者都把在线测量和自适应决策放进运行时。方向是从静态 capacity planning 转向不确定性下的 SLO／成本联合优化；未解之处包括预测分布漂移、近失约请求的公平性、极端突发，以及生产环境中控制开销的可验证上界。
