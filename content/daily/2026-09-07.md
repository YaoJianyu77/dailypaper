## Latest 1 — Efficient LLM Serving on Commodity GPU Clusters with Data-Reduced Cross-Instance Orchestration — EcoServe

**Latest · OSDI 2026 · July 2026 · Jiangsu Du, Hongbin Zhang, and colleagues.** [Official publication](https://www.usenix.org/conference/osdi26/presentation/du) · [Full paper](https://www.usenix.org/system/files/osdi26-du.pdf). Same work as [arXiv:2504.18154](https://arxiv.org/abs/2504.18154), originally titled *EcoServe: Enabling Cost-effective LLM Serving with Proactive Intra- and Inter-Instance Orchestration*.

### 1. Paper in brief

Separating prompt processing from token generation can improve serving throughput, but moving the intermediate state between servers becomes expensive on ordinary networks. Keeping both phases together avoids transfers but makes long prompt computations interrupt ongoing generation. EcoServe separates the phases in time within each instance, then coordinates several instances so that their prompt-processing windows occur in rotation. A request retains its state on one instance throughout execution. This exchanges frequent local interference and bulk network transfers for coordinated scheduling. P90 goodput = throughput at 90% latency-target attainment; across the L20 and A800 commodity-network experiments, EcoServe improves this by 2.01× over vLLM and 1.87× over Sarathi on average. Its main contribution is a serving architecture that exploits available latency slack; it does not establish a bound on every individual token delay. (§§3–4.2)

### 2. Problem and core insight

Prefill = processing a request’s input tokens; decode = generating subsequent tokens. The KV cache = saved attention keys and values reused during generation. The input is a stream of requests with unknown output lengths; the output is generated token streams. The objective is high goodput = sustainable request throughput at a required fraction of requests meeting latency targets, subject to GPU memory and network limits.

Two observations drive the design. Repeated prefill interruptions prevent large, efficient decode batches → longer uninterrupted phases improve utilization → separate phases temporally while retaining each request’s KV cache locally. However, a decoding instance cannot immediately accept a prefill → several instances can stagger their phases → coordinate them as a **macro instance = a group of cooperating serving instances**. Rolling activation provides prefill opportunities while other instances decode. The central resource being redistributed is time, rather than cached model state. (§§2–3.1)

### 3. How the method works

**Requests → macro-instance routing → latency and memory admission checks → local prefill → local batched decode, coordinated across instances → output tokens.**

The overall scheduler selects a macro instance. Its scheduler receives decode progress and memory-usage updates, then tries the instance that accepted the previous request; if unsuitable, it advances cyclically. Within an instance, new admitted prefills take priority, while decoding continues when no prefill is assigned. This groups prefills and lengthens decode periods without moving KV caches between serving instances. Communication required by a model distributed across GPUs still remains. (§3.3)

Admission checks three constraints. First, profiled prompt lengths estimate whether pending prefills fit the time-to-first-token target. Second, previously generated tokens create saved time-per-output-token slack: tokens produced multiplied by the target interval, minus elapsed generation time. Algorithm 1 compares the mean saved slack of existing decodes with pending prefill time. Third, the request’s required cache allocation must fit remaining memory. Consuming accumulated slack permits temporary prefill interruptions; profiling and repeated status exchange introduce control overhead.

Mitosis scaling = adding or removing individual instances, then splitting or merging their coordinating groups. Excess first-token latency triggers expansion; surplus decode slack signals contraction. A serializable instance handle transfers control between macro schedulers while model execution and caches stay in place. Removed instances drain assigned work before release. This avoids reloading models merely to reorganize groups, although genuinely new capacity still requires initialization. (§3.4)

The latency definitions matter: reported TTFT includes both actual first-token latency and the subsequent phase-switching wait. TPOT measurement starts after that switch. The design assumes frontend buffering can smooth generation into a steady display; its slack accounting does not mean every pair of token arrivals is equally spaced. (§3.2)

### 5. Experimental evidence

The testbeds comprise 64 L20-48GB GPUs over PCIe and 10-Gbps Ethernet, 16 A800-80GB GPUs over PCIe and 25-Gbps RoCE, and 16 H100-80GB GPUs with NVLink and eight 400-Gbps InfiniBand links per node. Models are Llama-30B, CodeLlama2-34B, and Qwen2-72B, all in BF16. EcoServe uses vLLM, Ray, and ZeroMQ; baselines are aligned to vLLM 0.7.3. Alpaca, ShareGPT, and LongBench use TTFT targets of 1, 5, and 15 seconds respectively, with 100-ms TPOT. Default arrivals follow a Poisson process. (§4.1)

Three findings support the claim. On L20/A800, average P90 goodput is 3.43× DistServe and 3.41× MoonCake, alongside the colocated-baseline gains above; avoiding cache transfer addresses the weak-network bottleneck, although implementation differences also contribute. On A800/ShareGPT, tightening targets from 5s/100ms to 1s/50ms reduces EcoServe’s P99 throughput from 42 to 18 requests/s, versus vLLM’s 16 to 6.4 and Sarathi’s 28 to 7.6: a substantial remaining advantage, but clear sensitivity to available slack. Finally, cyclic versus random activation and adaptive versus fixed-interval admission ablations favor EcoServe across all three models on A800/ShareGPT, supporting those scheduling choices without fully separating every source of end-to-end gain. (§§4.2–4.3, 4.7)

### 6. Contributions and limitations

The conceptual contribution is temporal separation combined with coordination across replicas. The system contribution is the macro-instance scheduler and logical regrouping mechanism. Its favorable setting is a medium-to-large model with usable latency slack and restricted interconnect bandwidth.

The authors acknowledge that small models can make interference negligible, while extremely tight targets or very large models may require full disaggregation and stronger hardware. MoonCake surpasses EcoServe for CodeLlama2-34B on H100; universal superiority is unsupported. DistServe’s prototype is unmaintained, and some baseline failures are omitted. Llama-30B truncates LongBench inputs at 2,048 tokens, complicating cross-model comparisons. (§§4.2, 5)

**Interpretation.** Mean-slack admission and frontend smoothing are insufficient evidence of a per-request maximum token-stall guarantee. Monetary savings and production failure recovery are not quantified. The paper’s throughput evidence is stronger than its broader engineering-simplicity and cost claims.

### 7. Final assessment

**Interpretation.** EcoServe convincingly demonstrates that coordinated timing can recover much of phase separation’s benefit while keeping request state local. The strongest evidence combines multiple networks, latency-target sweeps, and scheduling ablations. The weakest point is portability of the exact advantage across implementation versions and stricter token-level latency semantics. This is principally a system-design contribution, credible for the evaluated 30B–72B models and commodity-network configurations, with a clear boundary when insufficient latency slack prevents useful temporal separation.

## Latest 2 — Strata: Hierarchical Context Caching for Long Context Language Model Serving

**Latest · OSDI 2026 · Formal publication: July 2026 · Authors: Zhiqiang Xie et al.** [Official proceedings record](https://www.usenix.org/conference/osdi26/presentation/xie-zhiqiang) · [Full paper](https://www.usenix.org/system/files/osdi26-xie-zhiqiang.pdf). Identity: `arxiv:2508.18572`; USENIX record `318383`. The earlier preprint is the same work. July publication is verified; an earlier exact online-publication day is not specified by the official record.

### 1. Paper in brief

Long-context language-model serving can become limited by moving cached context back to the GPU, even after caching eliminates most prompt computation. Small GPU cache pages preserve reuse but fragment transfers; ordinary schedulers also launch batches whose computation cannot hide loading latency. Strata combines GPU-assisted transfers, different layouts for GPU and host memory, and scheduling that considers both cached data movement and pending cache creation. Its key change is treating host–GPU bandwidth as an explicit scheduling resource. On Llama-3.1-70B with LooGLE, it achieves up to 5× higher throughput than vLLM-LMCache and 3.75× than TensorRT-LLM with hierarchical caching, at the same average time to first token. The contribution is a coordinated cache-management and scheduling design, implemented in SGLang, rather than a model approximation (§§4–5).

### 2. Problem and core insight

KV cache = previously computed attention keys and values. Strata receives prompts containing reusable prefixes plus new tokens and produces generated text while minimizing time to first token, or TTFT, and increasing output-token throughput. It targets exact prefix reuse, dense attention, and primarily prefill-dominated workloads within one serving instance.

Small pages improve cache matching → enlarging pages to accelerate transfers sacrifices reuse → preserve fine GPU allocation while changing the transfer mechanism and host layout. For Llama-8B, 40 GB holds only about 300,000 cached tokens, making CPU memory valuable despite its slower connection (§§1, 3).

Long cached prefixes can require more loading than new-token computation can hide → a cache hit can still stall execution → form batches around both demands. Additionally, a **delay hit = a request for context whose first computation has not finished**; scheduling such requests together duplicates expensive prefill (§3.2).

### 3. How the method works

**Prompt → hierarchical prefix lookup → delay-hit deferral and balanced batching → cache loading overlapped with useful execution → prefill → continuous decoding → response and asynchronous cache backup.**

HiRadixTree = a prefix tree recording cache-page locations and status across memory tiers. The scheduler consults it while the current batch executes, and the cache controller initiates transfers for the next batch. CUDA events ensure each layer consumes its cached state only after loading finishes. Prefill and decoding share the GPU and alternate over time (§4.1).

Instead of issuing many small `cudaMemcpyAsync` calls, a CUDA kernel moves fragments using thousands of threads accessing pinned CPU memory. Few large thread blocks restrict interference with model execution; instructions bypass caches to reduce pollution. GPU pages remain layer-first, while host pages hold all layers together. An offset calculation transforms layouts during transfer, enabling larger contiguous storage transfers without imposing that layout on attention kernels (§4.2).

The scheduler records temporary tree nodes for queued or unfinished context creation. Requests sharing more than the default 100-token threshold are deferred to the next round and placed near the queue front. This converts redundant prefill into reuse once the originating request finishes.

Batch construction always begins with the oldest request, then favors combinations with enough new-token computation to cover cached-token loading. Requests sharing an already cached context are bundled because one load can serve several requests. A default load-to-compute token ratio of 100 marks loading pressure; the appropriate threshold depends on model and hardware. Deferred candidates retain their order, preventing starvation (§4.3).

If loading still leaves idle time, decoding fills the gap: it mainly consumes GPU-memory bandwidth while loading consumes the host link. For storage hits, best-effort prefetch overlaps queueing, then uses whatever has arrived at admission. Selective write-through backs up reused pages asynchronously; least-recently-used eviction manages capacity. These policies exchange extra metadata and scheduling work for less transfer and recomputation (§§4.3–4.4).

### 5. Experimental evidence

The main platform contains eight H200 GPUs, NVLink, an Intel Sapphire Rapids CPU, and 1.6 TB DRAM; each GPU has PCIe 5.0 ×16. Tests use one GPU for Llama-8B and Qwen-14B, four with tensor parallelism for Llama-70B, and 1 TB pinned host memory. Baselines use vLLM 0.8.5/LMCache 0.2.1, TensorRT-LLM 0.17.0, and SGLang 0.4.5. Strata uses one-token pages; hierarchical baselines generally use 32-token GPU pages (§5.1).

First, end-to-end gains support the combined design: LooGLE throughput at equal average TTFT improves by up to 2.6× over vLLM-LMCache for Llama-8B, 2.1× for Qwen-14B, and 5× for Llama-70B. These are conditional maxima, not average gains. NarrativeQA separately prewarms all CPU contexts and clears GPU caches; its results therefore characterize warm-cache operation (§5.2).

Second, ablations isolate useful components: scheduling alone raises peak throughput up to 1.8× and improved I/O alone up to 2.3× over SGLang-HiCache on Qwen-14B/LooGLE/H200. Their combined advantage supports addressing both bandwidth efficiency and batch composition (§5.3.1).

Third, the I/O microbenchmark reaches 48 GB/s with two 1,024-thread blocks, with under 5% prefill and 10% decode degradation during concurrent execution. This demonstrates the transfer/interference trade-off rather than cost-free copying (§4.2).

### 6. Contributions and limitations

The contributions are a layout-decoupling system design, a scheduling algorithm that accounts for pending cache creation and loading, and a GPU-transfer implementation with measured interference. Exact caching preserves model computation (§7).

The authors acknowledge uneven per-request treatment despite starvation prevention, possible service-level-objective violations, GPU resource contention, and incomplete coverage of sparse or linear attention (§6). Most benchmarks exclude disk; arrivals are synthetic Poisson processes capped at 128 concurrent requests. ShareGPT deliberately limits GPU cache capacity to about 500,000 tokens. **Interpretation:** these conditions support repeat-context serving claims more strongly than production tail-latency or arbitrary mixed-workload claims.

### 7. Final assessment

**Interpretation.** Strata convincingly demonstrates that expanding cache capacity requires joint transfer and scheduling design. Its strongest evidence is the combination of end-to-end comparisons and component ablations explaining why higher bandwidth alone is insufficient. Its weakest area is request-level latency guarantees under realistic arrival patterns. This is principally a systems contribution whose conclusions are strongest for dense-attention workloads with substantial prefix reuse and host-memory caching; benefits for sparse attention, large distributed cache pools, and strict tail-latency targets remain uncertain.

## Latest 3 — Optimal Software Pipelining and Warp Specialization for Tensor Core GPUs — Twill

Rupanshu Soi, Rohan Yadav, Fredrik Kjolstad, Alex Aiken, Maryam Mehri Dehnavi, Michael Garland, and Michael Bauer. **OSDI 2026**, pp. 1875–1890; official proceedings July 2026, publicly available by July 13. [Official publication](https://www.usenix.org/conference/osdi26/presentation/soi) · [Full paper](https://www.usenix.org/system/files/osdi26-soi.pdf). Research-work identity: arXiv:2512.18134; its December 19, 2025 preprint is the same work.

### 1. Paper in brief

Modern GPU kernels must coordinate matrix multiplication, scalar computation, and asynchronous data movement. Software pipelining = overlapping operations from different loop iterations; warp specialization = assigning different computations to independent groups of GPU threads. Choosing these separately can produce a theoretically fast pipeline that cannot execute efficiently because of registers, synchronization, or communication. Twill jointly solves both choices as constraints, finding the smallest feasible interval between iterations for a supplied hardware model. It rediscovers expert FlashAttention schedules on Hopper and Blackwell; a manually implemented Blackwell forward schedule comes within 2% of FlashAttention-4 at sequence length 16,384. Its main contribution is an optimization framework for discovering and explaining schedules, with guarantees restricted to the modeled problem. It does not automatically produce the complete high-performance CUDA implementation.

### 2. Problem and core insight

The input is a tiled loop, its data dependencies, instruction costs, and GPU resource capacities. The output specifies when each operation executes and which warps execute it. A warp = 32 threads executing together. The objective is maximum steady-state loop throughput, subject to dependencies and hardware constraints, rather than minimum latency for one isolated iteration (§§3–4).

Independent functional units create overlap opportunities → issuing everything through the same warp can lose that overlap at blocking waits → pipeline scheduling must include warp placement. Similarly, overlapping iterations extends live data lifetimes → registers can overflow → feasible schedules must jointly account for memory and cross-warp transfers. These transfers themselves add latency and synchronization, so distributing work across more warps is not automatically beneficial. Twill makes those interactions explicit instead of assuming fixed loader and compute roles.

### 3. How the method works

**Triton tiled loop → dependence graph and normalized hardware costs → initial pipeline → joint schedule-and-warp constraint solving → pipelined, warp-annotated intermediate code → implementation.**

Twill extracts operations and dependencies from Triton's GPU intermediate representation. Each operation has a resource reservation table = the functional units it occupies over time. Modulo scheduling = constructing a repeating schedule whose iterations start a fixed interval apart. An integer optimizer first finds the smallest initiation interval allowed by dependencies and functional-unit capacities (§5).

An SMT solver = a solver for logical and arithmetic constraints then revises the schedule while assigning warps. It enforces execution exactly once, consistent spacing between iterations, data dependencies, memory lifetimes, per-warp register budgets, cross-warp transfer costs, and conflicts caused by blocking synchronization. Twill represents a pipeline's prologue, one steady-state iteration, and epilogue as straight-line code; repeatability constraints make that finite representation describe the continuing loop. If the initial interval is infeasible, it explores schedule lengths and then larger intervals (Algorithm 1).

Cost normalization compresses cycle counts while approximately preserving their ratios, making solving tractable. Operations with unpredictable latency receive dedicated warps. Streaming loads without incoming dependencies can run ahead; their modeled latency becomes zero, while an external tuner chooses their prefetch depth (§5.3).

For Blackwell forward attention, the solution separates loads, matrix operations, two softmax groups, and accumulator rescaling. Softmax = converting attention scores into normalized exponential weights. Moving rescaling away from softmax prevents tensor-memory waits from interrupting exponentials; the solver also schedules the resulting communication. This is the concrete reason joint optimization matters.

Horizontal axis: sequence length; vertical axis: trillions of floating-point operations per second. Full Twill approaches the cuDNN and FA4 bars more closely than the separately combined scheduling variants. These are kernel measurements from manually implemented schedules, not an automatically compiled model or serving benchmark.*

### 5. Experimental evidence

Experiments use an NVIDIA H100 SXM5 with 80 GB and B200 with 180 GB, CUDA 13.0, and forward/backward fused attention. Plots fix batch 4, 32 heads, head dimension 128, FP16, and non-causal attention, varying sequence length from 2,048 to 16,384. Comparisons include Triton, direct CUDA translations, partial Twill variants, cuDNN, and the relevant FlashAttention implementation (§6).

Joint optimization matters most on Blackwell: at length 16,384, Twill's forward schedule comes within 2% of FA4. Adding Triton's warp-specialization heuristics to either the direct CUDA translation or the separately pipelined implementation provides no benefit. These controlled variants support the scheduling-interaction argument (§6.2.2).

Hopper is less demanding: the software-pipelining-only variant with Triton's warp assignment comes within 1% of FA3 at length 16,384. Full Twill is slightly worse after a separate data-multicasting optimization benefits the simpler schedule more. Optimality in the scheduling model therefore does not guarantee the fastest final binary (§6.2.1).

Search takes 18–242 seconds on one Intel Xeon Platinum 8570 core. Hopper forward takes 28 seconds, versus PipeThreader's reported 315 seconds for discovering the same strategy; this is a comparison with a reported result, not a controlled same-machine rerun. Table 1 also shows a Blackwell backward case increasing the feasible initiation interval from 15 to 20 after warp constraints are considered (§6.4).

### 6. Contributions and limitations

The conceptual contribution is treating warp specialization as part of realizing a pipeline; the algorithmic contribution is a joint constraint formulation; the system contribution is extracting and solving that formulation for real attention loops.

The implementation supports singly nested loops without additional control flow. Tile sizes and streaming depths remain external choices, and normalized costs approximate hardware timing. Evaluation covers two related attention kernels rather than a broad kernel suite. Most significantly, the authors manually translate schedules into CUDA because Triton's remaining lowering decisions are inadequate. Blackwell backward code still suffers register-allocation spills until they reduce the modeled register budget. Table 1 labels Blackwell cases “B100,” although §6.1 identifies the evaluation GPU as B200; the discrepancy is unresolved in the paper.

### 7. Final assessment

**Interpretation.** Twill convincingly demonstrates that important expert scheduling decisions can emerge from explicit constraints, especially when synchronization and register pressure make separate optimizations interact. Its strongest evidence combines rediscovered FlashAttention strategies with partial-system comparisons. Its weakest link is converting an optimal modeled schedule into efficient machine code: manual lowering, external tiling, and compiler allocation still matter. The contribution is principally an algorithmic scheduling framework realized as a compiler tool. Its conclusions are strongest for fixed tiled attention loops on the evaluated NVIDIA architectures, with an appropriate hardware model and substantial implementation support.

## Latest 4 — ParallelKittens: Systematic and Practical Simplification of Multi-GPU AI Kernels

Stuart H. Sul, Simran Arora, Benjamin F. Spector, and Christopher Ré. **MLSys 2026; first official online publication: May 18, 2026.** [Official proceedings](https://proceedings.mlsys.org/paper_files/paper/2026/hash/ff997469ac66cf893c4183efeb22212a-Abstract-Conference.html) · [Complete paper](https://proceedings.mlsys.org/paper_files/paper/2026/file/ff997469ac66cf893c4183efeb22212a-Paper-Conference.pdf) · [Supplement](https://proceedings.mlsys.org/paper_files/paper/2026/file/ff997469ac66cf893c4183efeb22212a-Supplemental-Conference.pdf)

### 1. Paper in brief

Fast distributed operators require communication to arrive when computation can use it, without consuming too many compute resources. Existing libraries and specialized kernels make this difficult through coarse transfers, restrictive synchronization, or complicated implementations. ParallelKittens, abbreviated PK, extends ThunderKittens with eight communication and synchronization primitives plus a reusable kernel template. Its insight is that transfer granularity, assignment of workers, and buffering overhead must be chosen together. Developers can place communication inside compute pipelines or on dedicated GPU cores. In a controlled eight-H100 experiment, changing the overlap schedule raises matrix-multiplication-plus-all-reduce throughput from 172.3 to 623.9 trillion floating-point operations per second. The contribution is a reusable programming system backed by hardware measurements and operator benchmarks; it does not establish equivalent acceleration for complete model serving.

### 2. Problem and core insight

Inputs are tensor shards distributed across GPUs; outputs are the corresponding matrix products, attention results, or expert-layer results after communication. The objective is minimum kernel time while preserving the computation. The core constraint is resource competition: SM = streaming multiprocessor, a GPU execution unit shared by computation and communication. More communication workers can hide transfers but remove workers from arithmetic.

**Observation → why it matters → design:** small transfers can saturate interconnects when initiated inside a kernel, whereas host copy engines need much larger contiguous messages → bulk communication interfaces waste opportunities for tile-level overlap → PK uses TMA = Tensor Memory Accelerator, an asynchronous hardware transfer unit, for ordinary transfers, and register instructions when switch-side reductions are required (§3.1.2).

**Observation → why it matters → design:** the best communication order need not match computation order → one scheduling policy cannot simultaneously maximize arithmetic occupancy, reuse remote data, and exploit network reductions → the template supports both intra-SM overlap, within an execution unit, and inter-SM overlap, across dedicated units (§3.1.3).

### 3. How the method works

**Sharded tensors → shared peer-memory mappings → tiled loading and computation → signaled transfers or reductions → distributed output tensors.**

The host establishes memory mappings between processes and preallocates destinations. PGL = Parallel Global Layout, PK's representation of equal-shaped memory regions on participating GPUs, lets device code address a peer tile directly. This avoids intermediate staging buffers. Network-accelerated operations require custom allocation and multicast mappings, adding setup and allocation constraints (§3.2; supplement E–F).

Four workers implement execution. The loader moves tiles from local or peer HBM = high-bandwidth GPU memory into shared memory. The consumer performs tensor-core or ordinary arithmetic. The storer writes completed tiles locally or remotely. A separate communicator can occupy dedicated SMs. Signals and waits express tile readiness; the template manages worker specialization, barriers, and resource partitioning.

Consider GEMM = general matrix multiplication followed by all-reduce, which combines partial results and gives every GPU the result. Compute workers accumulate a tile locally; the storer writes it to HBM and signals completion. The communicator waits until every GPU's corresponding tile is ready, then performs a network-accelerated reduction. Computation continues on other tiles. This changes repeated peer writes into coordinated reduction while overlapping its cost (supplement D).

Reduce-scatter, which retains a different portion of the reduced output on each GPU, instead benefits from embedding transfers inside the computation pipeline. For Ring Attention, dedicated communication workers stage remote key/value tensors locally for reuse: repeated direct peer reads otherwise cross NVLink repeatedly because remote data is cached at its source (§3.1.3).

### 5. Experimental evidence

The main evaluation uses eight H100 80-GB SXM GPUs, fourth-generation NVLink/NVSwitch, CUDA 12.8, and PyTorch 2.8.0. Matrix operands use BF16 with FP32 accumulation. Benchmarks use synthetic tensors and report operator compute throughput. Baselines include cuBLAS plus NCCL, Triton Distributed, Flux, CUTLASS, xDiT, YunChang, and Comet. Supplemental experiments use eight B200s (§4; supplement A, G).

**Scheduling matters → controlled ablation → exact throughput:** Figure 4 gives reduce-scatter 743.7 TFLOP/s with intra-SM overlap versus 618.1 with inter-SM overlap, about 1.20×. All-reduce reverses the result: 623.9 versus 172.3, about 3.62×; its no-overlap baseline is 450.9. These results support workload-specific scheduling, including the danger that an inappropriate overlap strategy slows execution.

**Communication can become nearly hidden → reduction-dimension sweep → measured latency:** at matrix dimensions M=N=32768 and K=4096, Table 3 reports 11.780 ms for standalone GEMM and 11.828 ms with reduce-scatter, under 1% exposed communication. At K=512, the corresponding times are 2.071 and 6.483 ms. Sufficient arithmetic per output tile, not overlap alone, explains the difference. The simplified analytical threshold is approximately K=2197 on the stated H100 parameters; synchronization and atomic accumulation keep the actual crossover approximate (§3.1.3).

### 6. Contributions and limitations

The conceptual contribution is an experimentally motivated decomposition of communication costs. The system contribution is the common memory abstraction and worker template. The engineering contribution is compact communication code added to optimized single-GPU kernels; the reported fewer-than-50-line count excludes the original computation implementation (§1).

Scope matters. The authors explicitly leave inter-node communication for future work. Expert-parallel evaluation covers token dispatch plus the first expert matrix multiplication, with performance ranging from 0.92× to 1.22× Comet (§4.3). **Interpretation:** neither operator throughput nor additional-code size measures complete deployment cost.

There is also a numerical inconsistency: §4.2 claims up to 4.08× Ring Attention speedup, but Figure 10's displayed bars have a largest ratio of 434/167, approximately 2.60×. The reason is **Not specified in the paper.** This report does not treat 4.08× as verified experimental evidence.

### 7. Final assessment

**Interpretation.** PK convincingly demonstrates that reusable abstractions can preserve important hardware choices rather than imposing one overlap policy. Its strongest evidence is the schedule ablation: more overlap can sharply reduce performance when it creates the wrong communication pattern. Its weakest points are the gap between operator benchmarks and complete applications, and the unresolved Ring Attention numerical discrepancy. The contribution is principally a programming-system design with a strong engineering realization. Its conclusions are most credible for carefully tuned, intra-node kernels on the evaluated Hopper and Blackwell platforms.

## Classic — Orca: A Distributed Serving System for Transformer-Based Generative Models

Gyeong-In Yu, Joo Seong Jeong, Geon-Woo Kim, Soojeong Kim, and Byung-Gon Chun. **OSDI 2022; official publication month: July 2022**, pp. 521–538. The first online day is not specified by the official record; the entire verified month lies within the classic window. [Official publication](https://www.usenix.org/conference/osdi22/presentation/yu) · [Full paper](https://www.usenix.org/system/files/osdi22-yu.pdf).

Continuing influence is concrete: the subsequent vLLM/PagedAttention paper uses Orca variants as baselines and explains how Orca’s iteration scheduling complements its memory management (§§2.2, 6.1, 8). These are later-system evidence, separate from the Orca results below. [vLLM paper](https://arxiv.org/pdf/2309.06180).

### 1. Paper in brief

Autoregressive serving = generating each next token from the preceding tokens. A request therefore requires many model iterations, but conventional serving fixes a batch until every request finishes. Completed requests wait unnecessarily, new arrivals cannot enter, and computation continues for inactive batch members. Orca changes scheduling to the iteration boundary and combines requests at different stages through selective batching: token-independent operations share a batch, while attention retains each request’s separate context. Its distributed engine also pipelines batches and separates CPU control messages from GPU tensor traffic. On a synthetic GPT-3-shaped 175-billion-parameter workload using 16 A100 GPUs, it sustains 6.81 versus 0.185 requests/s at approximately 190 ms/token median normalized latency. The contribution is a serving interface and execution design that converts variable-length generation into efficiently batchable work; its headline result measures serving throughput, not model quality.

### 2. Problem and core insight

The input is a prompt and a maximum token allowance; the output is generated text. The objective is high request throughput under a latency budget and finite GPU memory. The target is Transformer generation, including models whose parameters span multiple devices.

Two observations determine the design. **Repeated iterations → completion and admission need intermediate decision points → reschedule after each iteration.** This gives newly arrived requests a chance to enter without waiting for complete generations (§3). **Variable context lengths → attention tensors differ while most other operators remain token-independent → batch only compatible operations.** Attention here means the query–key scoring, softmax, and value aggregation, excluding the surrounding learned projections. Those projections retain parameter reuse across requests; attention itself has no model weights to amortize through batching.

### 3. How the method works

**Prompt → request pool → memory-aware admission → one batched model iteration across workers → generated token → repeat or return completed text.**

The scheduler chooses requests in arrival order, subject to a maximum batch size. It maintains iteration-level first-come-first-served ordering: an earlier request has completed at least as many iterations as a later one. Completion can still occur out of order when a later request needs fewer tokens. A newly admitted request processes its entire prompt in its first iteration; an ongoing request contributes its latest generated token (§§3–4.2).

Selective batching flattens these contributions into a tensor with shape `[sum of current input tokens, hidden size]`. Linear projections, normalization, residual additions, and feed-forward operations run on that combined tensor. Before attention, Orca splits it by request, retrieves that request’s KV cache = stored attention keys and values from previous tokens, and computes attention only within the correct sequence. It merges the outputs for subsequent batched operations. Thus varying prompt lengths and decoding positions coexist without mixing contexts. Although attention remains logically separate, implementation fuses different requests’ thread blocks into one kernel, reducing launch overhead (§5).

Before admission, the scheduler reserves KV capacity for the request’s maximum total token count. This prevents a deadlock in which every active request needs another cache slot but none can progress. Cache storage is released on completion. The cost is reserving space before all tokens exist (§4.2).

Tensor parallelism = splitting operations within a layer across GPUs; pipeline parallelism = placing different layer groups on successive workers. Orca keeps up to one batch per worker in flight, excludes already-running requests from selection, and reinserts their next iterations after results return. It pipelines separate batches without subdividing each into smaller microbatches. CPU controllers exchange scheduling metadata over gRPC; GPUs exchange tensors through NCCL. Separating these paths avoids GPU synchronization merely to deliver CPU-consumed metadata (§§4.1–5).

### 5. Experimental evidence

The evaluation uses Azure ND96asr A100 v4 machines: eight 40-GB A100 GPUs with NVLink per machine and 1.6 Tb/s aggregate intermachine InfiniBand. Models have 13B, 101B, 175B, or 341B parameters, FP16 weights/activations, and a 2,048-token sequence limit. The implementation contains approximately 13,000 C++ lines. Exact software version numbers: **Not specified in the paper.** (§§5–6).

First, the end-to-end comparison supports the scheduling claim: for 175B, 6.81 versus 0.185 requests/s gives the reported 36.9× improvement at about 190 ms/token median normalized latency. Prompts are uniformly 32–512 tokens; generated lengths are uniformly 1–128 tokens; arrivals are Poisson. FasterTransformer receives an authors-built dynamic-batching scheduler, with batch and microbatch configurations explored (§6.2, Figure 10).

Second, removing scheduling from the comparison yields similar or slightly worse Orca engine performance for 13B and comparable performance for 101B. For 175B, with pipelining disabled in both systems, the authors report up to 47% improvement and attribute it to control/data separation. This makes a universally faster kernel implementation an insufficient explanation for the end-to-end gain, although that experiment does not separately ablate every engineering difference (§6.1, Figure 9).

### 6. Contributions and limitations

The conceptual contribution is making a token-producing iteration the scheduling unit. The system contribution is selective batching plus a scheduler coordinated with memory admission and distributed execution. The engineering contribution includes fused attention launches and separate control/data communication.

The authors used neither actual model checkpoints nor actual input text; generation never emits an end-of-sequence token and always reaches the sampled limit. Consequently, the experiments establish execution behavior under controlled lengths, with no generation-quality evaluation. They acknowledge that batch-size increases can hurt latency under other workloads, and leave a general scheduler–engine interface to future work (§§6–7).

**Interpretation.** Large per-request limits can restrict concurrency through advance reservations. With few arrivals, there is little scheduling opportunity: the paper already observes no advantage for 101B under low load. Tail latency, long-context behavior beyond 2,048 tokens, and bursty production traffic remain unestablished.

### 7. Final assessment

**Interpretation.** Orca convincingly demonstrates that serving granularity can dominate the performance of otherwise comparable execution engines. Its strongest result connects an explicit admission/completion bottleneck to substantially higher throughput at a matched median latency. Its weakest point is workload realism: synthetic lengths and placeholder model inputs constrain what the absolute numbers establish. The main contribution is a system design built around two mutually necessary ideas, iteration scheduling and selective batching. Trust the causal argument for variable-length Transformer serving with enough concurrent requests; treat the 36.9× figure as a result for its stated baseline, hardware, and synthetic workload.

# Clear Research Trends in Today's Papers

**Competing GPU activities → joint placement and scheduling → model accuracy and implementation complexity.** Twill and ParallelKittens both show that adding concurrency is insufficient: synchronization, registers, memory locality, and worker placement determine whether overlap helps. Twill exposes these constraints to an optimizer; ParallelKittens gives programmers reusable mechanisms for choosing the arrangement. The remaining trade-off is how much hardware detail a compiler or programmer must model to obtain reliable gains across kernels and GPU generations. This is a signal from these two papers, not a claim that one scheduling strategy fits every workload.

**Expensive movement of inference state → scheduling around where data already resides → latency slack and fairness.** EcoServe keeps a request's cache local while coordinating prefill windows; Strata makes cache transfers and pending cache creation explicit inputs to scheduling. Both reduce unnecessary work by coordinating time with state placement, but their throughput advantages rely on workload structure and do not establish strict per-request tail-latency guarantees. Orca provides the historical connection: once execution can be scheduled between iterations, later systems can make finer decisions about when to compute, wait, or move state.
